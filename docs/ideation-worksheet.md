# 1. 서비스 선정

## 1.1 어떤 서비스의 장애를 자동 복구할 것인가?

**서비스 이름:** WorkGuide AI (Auto Healing 실습판)

**한 문장 설명:**

> 사용자가 **사내 자료에 대한 질문**을 요청하면, 서비스는 **권한 등급 안에서 매뉴얼·정책·경영자료·업무자료 아카이브를 검색하고 실제 LLM으로 답변을 생성·검증**한 뒤, **근거 문서와 인용 위치가 포함된 답변(절차형 질문은 실행 체크리스트 포함)**을 반환한다.

**정상 실행 흐름:**

```text
사용자 (권한 등급 + 질문)
  ↓
[ 질의 API: 요청 접수 → Policy Guard가 서버 측 권한 확인 ]
  ↓
[ 업무 처리 에이전트: Planner(질문 분석·경로 선택) → Retrieval(권한 내 검색·근거 수집)
  → Explanation(답변·체크리스트 생성) → Critic(원문 대조 검증),
  Memory Keeper가 단계별 상태와 중간 결과 보관 ]
  ↓
정상 결과: [ 근거 문서 ID·인용 위치를 포함한 구조화된 답변. 절차형 질문이면 실행 체크리스트 포함 ]
```

- **업무 처리 에이전트**(Planner, Retrieval, Explanation, Critic, Memory Keeper)는 장애를 겪는 *대상 서비스*를 구성한다.
- **장애 대응 에이전트**(Monitor, Diagnosis, Recovery, Verification, Orchestrator, Notification)는 가이드 기준 역할이다. 기획서의 Recovery Controller는 이 역할들로 나눠 반영했다.

**핵심 의존 서비스:**

| 의존 대상 | 용도 | 실패 시 영향 | 모의 구현 여부 |
|---|---|---|---|
| 실제 LLM API (기본 모델) | 질문 분석, 답변 생성, 검증 보조 | 응답 실패·지연, 형식 오류 | 실제 API 사용. 테스트 환경에서는 장애 주입 계층을 거침 |
| 실제 LLM API (대체 모델) | 기본 모델 장애 시 대체 경로 | 대체 경로 없음 → 에스컬레이션 | 실제 API 사용. 제공사와 모델은 [미결정] |
| 문서 검색 서비스 | 아카이브 검색, 권한·버전 필터 적용 | 검색 불가 → 캐시 폴백 또는 응답 보류 | 자체 구현 |
| 문서·상태 저장소 (DB) | 가상 문서와 메타데이터, 실행 상태·체크포인트 | 검색·상태 저장 불가 | 가상 데이터 사용 |
| 검증된 캐시 | 장애 시 권한 등급·문서 버전이 일치하는 이전 결과 재사용 | 폴백 경로 없음 | 자체 구현 |
| 에이전트 실행 프로세스(Worker) | 업무 처리 에이전트 실행 | 처리 중인 요청 중단 | 컨테이너로 실행 |

## 1.2 서비스가 멈추면 어떤 영향이 발생하는가?

### 사용자 영향

- 사내 자료에 대한 답변을 받지 못하거나 응답이 지연된다.
- 최악의 경우 근거나 날짜·금액·조건이 빠진 잘못된 답변을 받는다.

### 운영 영향

- 운영자가 로그를 직접 확인하고, 컨테이너를 재시작하고, 요청을 다시 보내야 한다.
- 장애 원인별 담당자가 정해져 있지 않아 대응이 늦어진다.

### 데이터·비용·보안 영향

- 가상 문서만 사용하므로 실제 데이터 손상과 개인정보 위험은 없다.
- 아카이브에 경영자료처럼 접근이 제한된 자료가 있다. 복구 중 권한 필터를 건너뛰면 하위 등급 사용자에게 경영자료가 노출될 수 있다. 따라서 **복구할 때도 권한은 절대 완화하지 않는다.**
- **실제 LLM을 사용하므로 비용 위험이 있다.** 재시도와 재생성이 반복되면 호출 비용이 늘어난다. 호출 상한과 비용 상한이 필요하다. 수치는 [미결정]이다.
- **LLM API 키를 보호해야 한다.** 저장소나 로그에 키가 노출되면 안 된다.

### 심각도

- [ ] 낮음 — 지연되지만 핵심 기능은 유지됨
- [x] 중간 — 일부 요청이 실패하고 운영자 대응이 필요함
- [ ] 높음 — 핵심 기능이 중단되거나 데이터·금전 피해 가능

**선택 근거:** 질의 요청이 실패하고 운영자 대응이 필요하다. 가상 데이터만 쓰므로 실제 피해는 없다. 권한 노출 위험은 설계 원칙으로 통제한다.

## 1.3 현재 사람은 장애를 어떻게 발견하고 복구하는가?

| 단계 | 현재 사람의 행동 | 사용하는 정보·도구 | 소요시간 | 문제점 |
|---|---|---|---:|---|
| 탐지 | 사용자 문의나 오류 화면으로 장애를 인지한다 | 사용자 제보, 서비스 로그 | [미결정] | 사용자가 먼저 겪은 뒤에야 알게 된다 |
| 진단 | 로그를 읽고 LLM·검색·DB·컨테이너 중 무엇이 문제인지 판단한다 | 서비스 로그, 컨테이너 상태 | [미결정] | 판단이 사람마다 다르고 근거가 남지 않는다 |
| 복구 | 컨테이너를 재시작하고 실패한 요청을 다시 보낸다 | 수동 재시작, 요청 재전송 | [미결정] | 처음부터 다시 처리하므로 중복 호출과 비용이 생긴다 |
| 검증 | 같은 질문을 다시 보내 응답을 눈으로 확인한다 | 수동 질의 | [미결정] | 근거·조건 누락이나 권한 노출을 놓칠 수 있다 |
| 보고 | 메신저로 공유한다 | 메신저 | [미결정] | 담당자 지정과 복구 시간 기록이 없다 |

> 소요시간은 실측 근거가 없으므로 `[미결정]`으로 둔다. 자동화 후 MTTD·MTTR과 비교할 기준선으로만 사용한다.

**자동화하려는 단계:** 탐지, 진단(정의된 장애 분류), 허용된 범위 내 복구, 복구 결과 독립 검증, 사건 기록, 담당자 알림

**사람이 계속 담당해야 할 단계:** 원인을 알 수 없는 장애 판단, 회로 차단 이후 대응, 허용목록 밖 조치의 승인, 에스컬레이션된 사건 처리

## 1.4 3일 동안 재현 가능한 최소 서비스는 무엇인가?

### 포함 범위

- **아카이브 대상:** 매뉴얼, 정책, 경영자료, 업무자료의 4개 유형. 가상 문서 10~12개(유형별 2~3개)
- **아카이브 방식:** 미리 정리한 가상 문서를 메타데이터와 함께 적재. 관리자 등록 기능은 최소로만 둔다. 메타데이터 구조는 후속 단계의 업로드·자동 파싱 경로도 같은 구조로 등록할 수 있게 설계한다.
- **권한:** 3등급 (예: 일반 직원 / 팀장 / 경영진). 경영자료는 상위 등급만 접근할 수 있다. 등급 명칭과 자료별 접근 매핑은 [미결정]
- **질문 유형:** 절차형(체크리스트), 정보형(요약), 여러 문서에 걸친 질문(문서별 근거 제시), 권한 밖 요청(차단), 근거 부족(보류)
- **업무 처리 에이전트:** Planner, Retrieval, Explanation, Critic, Memory Keeper + Policy Guard. Critic 검증에 실패하면 수정 루프는 최대 2회
- **장애 대응 역할:** Monitor, Diagnosis, Recovery, Verification, Orchestrator, Notification
- **복구 경로:** 실제 LLM 기본·대체 모델, 테스트 환경 전용 장애 주입 계층, 검증된 캐시 폴백, 체크포인트 재개, DB 재연결
- **배포:** 멀티 컨테이너 배포 매니페스트 (평가 기준 P3-2: Pod/Service, 서비스 디스커버리, 로드밸런싱, 시크릿 관리)
- **파이프라인:** 커밋 → 빌드 → 테스트(단위·통합) → 배포 (평가 기준 P3-3)
- **알림:** 실행 결과 자동 알림, 담당자 할당·에스컬레이션 (평가 기준 P3-3)
- **측정:** 테스트 질문 20개, MTTD·MTTR, 수동 개입 없는 복구 비율
- **저장소:** 공개 또는 조직 공유 GitHub 저장소 (평가 기준 P3-0)

### 제외 범위

- 제품로그 자료 유형
- 사용자 문서 업로드와 자동 파싱 (최종 형태이지만 후속 범위), PDF·이미지 파싱, OCR
- 실제 기업 데이터 연동, 복잡한 SSO·조직도 연동, 전사 업무 시스템 통합
- 문서 자동 신청·결재, 장기 메모리, 고급 관리자 대시보드
- 문서 간 규정 충돌 분석·변경 영향 분석
- 기획서의 특정 기술스택 확정 (평가 기준이 요구하는 항목만 제약조건으로 기록)
- 다중 서버 고가용성, 클라우드 운영 환경 배포
- LLM이 생성한 명령의 자동 실행, 허용목록 밖 재시작, 비용 상한이 없는 호출·확장

### 사용할 환경

- [ ] 로컬 프로세스
- [ ] Docker Compose
- [x] Kubernetes 로컬 클러스터 — 평가 기준 P3-2(Pod/Service 매니페스트)를 직접 충족
- [ ] 클라우드 샌드박스
- [x] 기타: 파이프라인의 배포 단계는 테스트 실행 환경에 임시 클러스터를 띄워 배포하고 스모크 테스트까지 수행

### 선택한 장애 유형

평가 기준 P3-2의 감지 범주(네트워크·DB·API·LLM·프롬프트)와 복구 방식(재시작·재연결·대체 모델·캐시 폴백)을 모두 다루도록 5종을 정했다.

| 코드 | 장애 | 평가 감지 범주 | 대표 복구 방식 |
|---|---|---|---|
| F1 | LLM API 오류·응답 지연 (HTTP 5xx, 429, 타임아웃) | API·LLM | 재시도 → 대체 모델 |
| F2 | 프롬프트·출력 오류 (잘못된 JSON 구조, 필수 조건·근거 누락) | 프롬프트 | 누락 항목을 전달해 재생성 (최대 2회) → 대체 모델 재생성 |
| F3 | DB 연결 실패 | DB | 재연결 → 체크포인트 재개 |
| F4 | 작업 중 Worker 컨테이너 종료 | 프로세스·컨테이너 | 재시작 → 저장된 단계부터 재개 |
| F5 | 문서 검색 장애 (검색 서비스 오류·연결 실패·타임아웃) | 네트워크·API | 재연결 → 권한·버전이 일치하는 캐시 폴백 |

- **반복 장애·복구 불가:** 개별 장애가 아니라 공통 정책으로 다룬다. 회로를 차단하고, 근거 없는 답변을 막고, 담당자에게 알린다. 데모에서는 F1을 지속시켜 검증한다.
- **보안 검증 S1:** 하위 등급 사용자가 경영자료를 요청하는 경우다. 장애가 아니며, 복구 성공률 계산에서 제외한다.

# 2. 에이전트 설계

## 2.0 전체 구성과 구조 선택 근거 (평가 기준 P3-1)

| 계층 | 구성요소 | 구현 방식 |
|---|---|---|
| 업무 처리 | Planner, Retrieval, Explanation, Critic | LLM 사용 에이전트. 단계별 LLM 사용 범위는 [미결정] |
| 업무 처리 | Policy Guard (권한 확인) | 프로그램 로직. LLM을 쓰지 않는다 |
| 업무 처리 | Memory Keeper | 프로그램 로직 (상태·중간 결과·체크포인트 저장소) |
| 장애 대응 | Monitor, Diagnosis, Recovery, Verification, Orchestrator, Notification | 규칙·상태기계 중심. 원인 불명 판단 보조에 LLM을 쓸지는 [미결정] |

**구조 선택 근거** (평가 기준: 응답 속도, 결정 일관성, 장애 격리)

- **응답 속도:** Planner가 질문 유형에 따라 필요한 단계만 실행한다. 권한 밖 요청은 LLM 호출 없이 차단한다.
- **결정 일관성:** 권한 판단은 LLM이 아니라 백엔드 규칙(Policy Guard)이 먼저 한다. Retrieval은 허용된 문서만 검색한다. Critic이 원문과 날짜·금액·조건을 대조한다.
- **장애 격리:** 업무 처리와 장애 대응을 분리한다. 한 단계가 실패해도 Memory Keeper의 체크포인트부터 재개하고, 회로 차단으로 장애가 다른 요청으로 번지지 않게 한다.

> 가이드 원칙: 규칙으로 충분한 역할은 LLM 에이전트로 분리하지 않는다. 에이전트 수를 늘리는 것이 목표가 아니다.

### 업무 처리 에이전트 요약

| 에이전트 | 책임 | 입력 | 출력 | 금지 행동 |
|---|---|---|---|---|
| Planner | 질문 의도·유형 분류, 실행 경로 선택 | 질문, 검증된 권한 등급 | 실행 계획 | 권한 판단을 직접 하지 않음 |
| Retrieval | 허용 범위 내 문서 검색, 관련 조항 추출, 근거 연결 | 실행 계획, 허용 문서 범위 | 문서 ID·버전·인용 위치·원문 발췌 | 권한 밖 문서 검색 |
| Explanation | 쉬운 설명, 행동 항목·체크리스트 작성 | 검색 근거, 질문 유형 | 답변 초안 | 근거 없는 내용 생성 |
| Critic | 원문 대비 날짜·금액·조건·준비물·근거 검증 | 답변 초안, 원문 근거 | 통과 / 수정 요청(누락 항목 포함) / 보류 | 근거 없이 통과 처리 |
| Memory Keeper | Handoff 상태·중간 결과·체크포인트 보관 | 각 단계의 출력 | 저장된 상태, 재개 지점 | 검증되지 않은 상태를 재개 지점으로 제공 |

### Handoff 상태 (개념 수준, 평가 기준 P3-1)

요청 ID, 질문, 서버에서 검증한 권한 등급, 질문 유형과 적용 기준일, 실행 계획과 현재 단계, 검색 문서 ID·버전·인용 위치·원문 근거, 추출된 핵심 조건(날짜·금액·조건·준비물), 답변 초안과 검증 결과, 수정 루프 횟수, 오류 유형·시도 횟수·복구 상태

- 단계가 넘어갈 때마다 필수 필드가 모두 있는지 확인한다. 하나라도 빠지면 다음 단계로 넘기지 않는다.
- 실제 스키마는 상세 설계 단계에서 확정한다.

## 2.1 장애를 탐지하는 주체는 누구인가?

**에이전트 이름:** Monitor

**관찰 데이터:**

- [x] 헬스체크 응답 (API, Worker, 검색 서비스, DB, LLM 연결)
- [x] 애플리케이션 로그
- [x] 오류율
- [x] 응답시간
- [x] 프로세스 상태 (컨테이너 상태)
- [x] 기타: 출력 구조 검증 결과, Critic 검증 결과, Handoff 필수 필드 누락

**유형별 감지 메트릭** (평가 기준 P3-2)

| 범주 | 메트릭 | 판정 조건 |
|---|---|---|
| 네트워크 | 서비스 간 연결 실패 수, 연결 타임아웃 | 연속 3회 실패 |
| DB | 연결 실패 수, 쿼리 오류율 | 연속 3회 실패 |
| API | LLM API·검색 서비스의 상태 코드 분포(5xx, 429), 오류율 | 오류 발생 시 재시도 대상. 연속 3회면 대체 경로 |
| LLM | 호출 지연시간, 타임아웃 발생 수, 토큰·비용 사용량 | 호출 10초 초과 시 타임아웃. 비용 상한 [미결정] |
| 프롬프트 | 출력 구조 오류율, 필수 조건·근거 누락률 | 검증 실패 1건 발생 시 |
| 컨테이너 | 헬스체크 실패, 재시작 횟수 | 연속 3회 실패 |

**출력 메시지:** 사건(incident) 정보. 개념적 필드는 사건 ID, 요청 ID, 대상 구성요소, 감지 범주, 관찰된 신호, 탐지 시각, 원본 증거다. 실제 스키마는 상세 설계에서 확정한다.

---

## 2.2 원인을 진단하는 주체는 누구인가?

**에이전트 이름:** Diagnosis

**입력:** Monitor가 만든 사건 정보, 관련 로그와 상태 증거, 같은 요청과 같은 구성요소의 이전 시도 이력

**분류할 장애 유형:**

| 장애 코드 | 설명 | 판단 근거 | 신뢰도 또는 규칙 |
|---|---|---|---|
| F1_LLM_API | LLM API 오류·응답 지연 | 상태 코드 5xx·429, 호출 시간 초과 | 규칙 기반 |
| F2_PROMPT_OUTPUT | 출력 구조 오류, 필수 조건·근거 누락 | 구조 검증 실패, Critic 검증 실패 | 규칙 기반 |
| F3_DB_CONN | DB 연결 실패 | 연결 오류, DB 헬스체크 실패 | 규칙 기반 |
| F4_WORKER_DOWN | Worker 컨테이너 종료 | 헬스체크 실패, 컨테이너 종료 상태 | 규칙 기반 |
| F5_SEARCH | 문서 검색 장애 | 검색 서비스 오류 응답·연결 실패·타임아웃 | 규칙 기반 |
| REPEATED | 동일 장애 반복·복구 불가 | 시도 상한 초과, 대체 경로도 실패 | 규칙 기반 (시도 이력) |
| UNKNOWN | 분류 불가 | 위 규칙에 해당하지 않음 | 자동 복구하지 않음 |

**원인을 판단할 수 없을 때 행동:** 자동 변경 없이 `UNKNOWN`으로 분류하고 Orchestrator를 통해 담당자에게 에스컬레이션한다. 원인을 추측해 복구안을 만들지 않는다.

---

## 2.3 복구를 실행하는 주체는 누구인가?

**에이전트 이름:** Recovery

**허용된 복구 행동** (평가 기준 P3-2: 재시작·재연결·대체 모델·캐시 폴백)

- 기본 모델 재시도 (제한된 횟수, 백오프 적용)
- 대체 모델로 전환 (사전에 승인된 대체 경로)
- 누락 항목을 전달해 재생성, 잘못된 구조 재생성
- DB·검색 서비스 재연결
- 허용목록에 등록된 Worker 컨테이너 재시작
- 마지막 유효 체크포인트부터 재개 (재개 전 권한과 문서 유효성 재확인)
- 검증된 캐시 폴백 (권한 등급·문서 버전 재확인을 통과한 캐시만 사용, 응답 상태는 DEGRADED)

**금지된 행동:**

- 권한 필터를 완화하거나 건너뛰기
- 검증되지 않은 문서·캐시를 근거로 사용하기, 근거 없는 답변 내보내기
- LLM이 생성한 임의 명령 실행
- 허용목록 밖 컨테이너·서비스 재시작
- 문서·상태 데이터 삭제 또는 임의 수정
- 비용 상한을 넘는 LLM 호출
- 스스로 복구 완료 선언 (완료 판정은 Verification이 한다)

**필요한 도구·API·명령:** 개념 수준으로만 정한다. 모델 경로 전환, 재시도 실행, 재연결, 허용목록 기반 재시작, 체크포인트 조회·재개, 캐시 조회가 필요하다. 구체적인 명령과 스크립트는 [미결정]이며 다음 단계에서 정한다.

---

## 2.4 복구 성공을 독립적으로 검증하는 주체는 누구인가?

**에이전트 이름:** Verification

**독립성이 필요한 이유:** Recovery가 성공했다고 보고해도 실제로는 출력 오류가 남아 있거나, 권한이 바뀌었거나, 같은 단계가 중복 실행됐을 수 있다. 그래서 복구 수행 주체와 다른 주체가 정상 상태를 확인해야 한다.

> 업무 처리의 Critic은 *답변 내용*을 검증한다. Verification은 *복구 후 서비스 정상화*를 검증한다. 두 역할은 겹치지 않는다.

**검증 항목:**

- [x] 헬스체크 정상
- [x] 핵심 기능 테스트 통과 (기준 질문을 다시 처리해 근거가 포함된 구조화된 답변이 반환되는지 확인)
- [x] 오류율 정상 범위
- [x] 응답시간 정상 범위
- [x] 데이터 무결성 확인 (근거 문서 ID가 실제 존재하고 권한 내 문서인지, 단계 중복 실행이 없는지)
- [x] 회귀 테스트 통과 (파이프라인의 권한·근거 회귀 테스트 세트)

**복구 실패 판정 조건:** 위 검증 항목 중 하나라도 실패하면 복구 실패다. 권한 밖 문서가 노출되면 즉시 실패로 처리하고 자동 복구를 중단한다. 정상 범위의 수치는 [미결정]이다.

---

## 2.5 오케스트레이터가 필요한가?

- [x] 필요함
- [ ] 필요하지 않음

**판단 근거:** 탐지 → 진단 → 복구 → 검증의 순서와 사건 상태를 한곳에서 관리해야 한다. 시도 횟수, 회로 차단, 비용 상한, 전체 타임아웃을 역할별로 흩어 두면 무한 복구 루프와 비용 폭증을 막을 수 없다.

### 오케스트레이터의 책임

- 사건 상태 관리 (탐지됨 → 진단됨 → 복구 중 → 검증 중 → 복구됨 / 기능 축소 / 실패 / 에스컬레이션)
- 역할 호출 순서와 사건별 시도 횟수 관리
- 회로 차단, 냉각시간, 전체 워크플로 타임아웃, LLM 호출·비용 상한 적용
- 상한 초과, `UNKNOWN`, 검증 실패 시 Notification을 통한 담당자 에스컬레이션

### 오케스트레이터가 해서는 안 되는 일

- 재시도 상한, 회로 차단, 비용 상한, 권한 제한 정책 우회
- 서비스·컨테이너·데이터 직접 조작 (복구 행동은 Recovery만 수행)

> 업무 처리의 실행 순서는 Planner가, 장애 대응의 실행 순서는 Orchestrator가 관리한다. 기획서의 Orchestrator가 맡던 "질문 분석"은 Planner로 옮겼다.

## 2.6 에이전트 협업 구조

| 에이전트 | 입력 | 출력 | 호출 주체 | 허용 권한 | 타임아웃 |
|---|---|---|---|---|---:|
| Monitor | 헬스체크, 로그, 유형별 메트릭 | 사건 정보 | 주기 실행 또는 오류 발생 시 | 조회, 사건 생성 | [미결정] |
| Diagnosis | 사건 정보, 증거, 시도 이력 | 장애 코드, 근거, 권장 복구전략 | Orchestrator | 증거 조회, 복구안 제안 | [미결정] |
| Recovery | 장애 코드, 승인된 복구전략 | 수행 결과(행동, 시도 횟수, 결과) | Orchestrator | 허용목록 내 재시도, 대체 전환, 재생성, 재연결, 재시작, 체크포인트 재개, 캐시 폴백 | [미결정] |
| Verification | 사건 정보, 복구 수행 결과 | 검증 결과(통과/실패, 항목별 근거) | Orchestrator | 헬스체크, 기준 질문 처리, 근거·권한 확인 | [미결정] |
| Notification | 최종 사건 상태, 증거, 권장 조치 | 알림 메시지, 담당자 할당, 에스컬레이션 기록 | Orchestrator, 파이프라인 | 알림 발송, 승인·확인 요청 | [미결정] |

### 협업 흐름

```text
[장애 발생]
  ↓
[ Monitor: 유형별 메트릭 관찰 → 사건 생성 ]
  ↓
[ Orchestrator: 사건 등록, 시도 횟수·회로·비용 상한 확인 ]
  ↓
[ Diagnosis: 장애 코드 분류(F1~F5 / REPEATED / UNKNOWN) ]
  ↓
[ Recovery: 허용된 복구전략 실행 ]
  ↓
[ Verification: 복구 결과 독립 검증 ]
  ├─ 성공 → [ RECOVERED 또는 DEGRADED(캐시 폴백) 처리, Notification이 결과 알림 ]
  └─ 실패 → [ 상한 내면 다음 전략, 상한 초과·UNKNOWN이면 회로 차단·근거 없는 답변 차단 후 Notification이 담당자 에스컬레이션 ]
```

# 3. 자율성과 통제

## 3.1 자동으로 실행해도 되는 복구는 무엇인가?

| 복구 행동 | 자동 허용 이유 | 영향 범위 | 선행조건 | 실행 후 검증 |
|---|---|---|---|---|
| 기본 모델 재시도 (백오프) | 일시적 오류에 효과적이고 데이터를 바꾸지 않음 | 해당 요청 | 시도 횟수·비용이 상한 미만, 회로 닫힘 | 출력 구조·근거 검증 |
| 대체 모델 전환 | 사전에 승인된 대체 경로임 | 해당 요청 또는 회로가 열린 동안 | 기본 모델 재시도 상한 도달, 대체 모델 헬스체크 정상 | 구조·근거 검증, 기준 질문 처리 |
| 누락 항목 전달 재생성 | 잘못된 출력을 폐기할 뿐 상태를 바꾸지 않음 | 해당 요청 | 수정 루프 2회 미만 | 구조·근거·권한 재검증 |
| DB·검색 서비스 재연결 | 연결만 다시 맺고 데이터를 바꾸지 않음 | 해당 연결 | 재연결 횟수가 상한 미만 | 헬스체크, 저장된 상태·검색 조회 |
| 허용목록 Worker 재시작 | 허용목록 대상이며 상태는 체크포인트에 있음 | Worker 1개 | 허용목록 포함, 재시작 횟수가 상한 미만 | 헬스체크, 기준 질문 처리 |
| 체크포인트부터 재개 | 저장된 유효 상태만 사용함 | 해당 요청 | 체크포인트의 권한·문서 유효성 재확인 통과 | 단계 중복 여부, 최종 응답 검증 |
| 검증된 캐시 폴백 | 이미 검증된 정보만 제공함 | 해당 요청 | 같은 권한 등급·유효 버전의 캐시 존재 | 캐시 권한·버전 재확인, DEGRADED 표시 |

## 3.2 사람의 승인이 필요한 복구는 무엇인가?

| 복구 행동 | 승인 필요 이유 | 승인자 | 승인 타임아웃 | 미승인 시 행동 |
|---|---|---|---:|---|
| 회로 차단 해제 전 강제 재개 | 반복 장애의 원인이 해소됐는지 사람이 판단해야 함 | 장애 유형별 담당자 [미결정] | [미결정] | 회로 유지, 자동 복구 중단 |
| 문서·메타데이터 수정 | 답변 정확성과 권한에 직접 영향 | [미결정] | [미결정] | 변경하지 않음 |

## 5.2 장애 탐지부터 복구까지 걸린 시간을 어떻게 측정할 것인가?

```text
injected_at  = 장애 주입 계층이 장애를 활성화한 시각
detected_at  = Monitor가 사건을 생성한 시각

recovered_at = Verification이 정상 판정을 내린 시각
```

```text
MTTD = detected_at - injected_at
MTTR = recovered_at - injected_at
복구 실행시간 = recovered_at - recovery_started_at
```

**시간을 기록할 컴포넌트:** 장애 주입 계층(injected_at), Monitor(detected_at), Recovery(recovery_started_at), Verification(recovered_at)

3. 장기 메모리, 고급 관리자 대시보드, 문서 충돌·변경 영향 분석, 다중 서버 고가용성

## 성공 기준

1. 테스트 질문 20개에서 완료율 90% 이상, 날짜·금액·조건 보존율 95% 이상, 권한 위반 0건
2. F1~F5 주입 실험마다 탐지·복구·검증 결과와 MTTD·MTTR이 기록되고, 수동 개입 없는 복구 비율이 80% 이상이다.
3. 반복 장애에서 회로가 열리고 담당자에게 자동 알림이 가며, 필수 테스트가 실패하면 배포가 차단된다.
