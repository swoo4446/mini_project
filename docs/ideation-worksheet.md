# 1. 서비스 선정

## 1.1 어떤 서비스의 장애를 자동 복구할 것인가?

**서비스 이름:** OrderOps AI (브랜드 선택형 단체 주문 취합·정산 서비스)

**한 문장 설명:**

> 사용자가 단체 채팅 주문 대화와 주문 브랜드를 입력해 분석을 요청하면, 서비스는 주문 해석 의존 서비스와 선택한 브랜드의 메뉴 데이터를 이용해 주문을 추출·정규화·검증하고, 개인별 확인과 담당자 확정을 거쳐 매장 주문서와 개인별 정산 내역을 반환한다.

의존 서비스가 실패·지연되거나 처리 프로세스가 중단되면, 복구 워크플로가 장애를 탐지하고 제한된 복구를 수행한 뒤 정상화 여부를 독립적으로 검증한다.

**정상 실행 흐름:**

```text
주문 담당자
  ↓  채팅 대화 붙여넣기([이름] 메시지 형식) + 카페 브랜드 선택 (한 화면, 순서 무관)
[주문 서비스 — 주문 이벤트 추출 → 브랜드 메뉴 정규화 → 주문 검증]
  ↓  ↔ 주문 해석 서비스 / 브랜드 메뉴·상태 저장소
[담당자 검토·수정 → 개인 확인 링크 전달 → 주문 참여자 확인·수정 요청]
  ↓
[전체 확정 조건 충족 → 담당자 최종 확정 → 집계·정산]
  ↓
정상 결과: [매장 주문서 + 개인별 정산 내역 + 주문 처리 결과(변경·확인·검증·복구 이력)]
```

**핵심 의존 서비스:**

| 의존 대상 | 용도 | 실패 시 영향 | 모의 구현 여부 |
|---|---|---|---|
| 주문 해석 서비스 (1차) | 자연어 대화에서 주문 추가·수정·취소·확정 이벤트 추출 | 분석 중단·지연 | 모의 구현 (고정 응답, 5xx·지연 모드 전환 가능). MVP는 모의 응답으로 우선 진행하고 실제 LLM 연결은 후순위 |
| 대체 주문 해석 서비스 | 1차 서비스 장애 시 사전 승인된 대체 경로 | 대체 불가 시 에스컬레이션 | 모의 구현 (1차와 독립적으로 장애 모드 전환 가능) |
| 브랜드 메뉴·상태 저장소 | 브랜드별 메뉴·옵션·가격 확인, 작업 상태·체크포인트·주문·확인 상태 저장 | 메뉴 검증·정산 불가, 중단 작업 재개 불가 | 가상 카페 브랜드 시드 데이터 사용 |
| 주문 처리 프로세스 (Worker) | 분석·검증·정산 단계 실행 | 진행 중 작업 중단, 중복·유실 위험 | 실습 전용 환경의 프로세스 |

**사용자 구분:**

| 사용자 | 주요 목적 |
|---|---|
| 주문 담당자 | 주문 취합, 오류 수정, 개인 확인 요청, 최종 확정, 주문서 생성 |
| 주문 참여자 | 자신의 주문 내역·금액 확인 또는 수정 요청 (회원가입 없음) |
| 서비스 운영자 | 장애 탐지·복구 상태 확인, 복구 승인 |

## 1.2 서비스가 멈추면 어떤 영향이 발생하는가?

### 사용자 영향

- 주문 담당자는 분석·검토 결과나 주문서·정산표를 받지 못해 수기로 다시 정리해야 한다.
- 주문 참여자는 개인 확인을 진행하지 못하거나, 장애 중 변경된 내용으로 재확인을 요구받을 수 있다.

### 운영 영향

- 운영자가 장애를 직접 발견하고 원인을 확인한 뒤 작업을 수동으로 재실행해야 한다.
- 재실행 후 주문 중복·유실과 개인 확인 상태의 정합성을 수동으로 점검해야 한다.

### 데이터·비용·보안 영향

- 가상 브랜드·메뉴와 가명 데이터만 사용하므로 실제 결제·개인정보 위험은 없다.
- 재처리 과정에서 주문이 중복 반영되거나 유실되어 정산 금액이 틀릴 수 있다.
- 개인 확인 링크는 링크 보유 여부로만 접근을 판단하므로, 링크가 노출되면 해당 주문자의 주문 내역이 보일 수 있다.

### 심각도

- [ ] 낮음 — 지연되지만 핵심 기능은 유지됨
- [x] 중간 — 일부 요청이 실패하고 운영자 대응이 필요함
- [ ] 높음 — 핵심 기능이 중단되거나 데이터·금전 피해 가능

**선택 근거:** 장애 시 분석 요청이 실패하고 운영자의 수동 재처리가 필요하지만, 실제 결제·송금이 없어 금전 피해로 직결되지 않는다.

## 1.3 현재 사람은 장애를 어떻게 발견하고 복구하는가?

| 단계 | 현재 사람의 행동 | 사용하는 정보·도구 | 소요시간 | 문제점 |
|---|---|---|---:|---|
| 탐지 | 사용자가 결과가 나오지 않는다고 알리거나 운영자가 화면을 보고 발견 | 사용자 문의, 화면 | [미결정] | 발견이 늦고 사람에 의존 |
| 진단 | 로그를 열어 의존 서비스 오류·지연·프로세스 중단 여부 확인 | 애플리케이션 로그 | [미결정] | 장애 유형 판단 기준이 없음 |
| 복구 | 프로세스 재시작, 작업 처음부터 재실행 | 수동 재시작, 재요청 | [미결정] | 전체 재처리, 중복 위험 |
| 검증 | 결과 화면을 보고 주문·금액이 맞는지 눈으로 확인 | 결과 화면 | [미결정] | 중복·유실 확인이 불완전 |
| 보고 | 메신저로 구두 공유 | 메신저 | [미결정] | 기록·추적이 남지 않음 |

**자동화하려는 단계:** 탐지, 진단(규칙 기반 장애 분류), 허용된 범위의 복구, 독립 검증, 결과 기록

**사람이 계속 담당해야 할 단계:** 개인별 주문 확인과 최종 확정(업무 승인), 원인 불명 장애 처리, 회로 차단 이후 조치, 자동 복구 실패 후 판단

## 1.4 3일 동안 재현 가능한 최소 서비스는 무엇인가?

### 포함 범위

- 채팅 입력과 카페 브랜드 선택을 한 화면에서 순서 무관하게 처리. 둘 다 입력되어야 분석 시작
- 가상 카페 브랜드 2개, 브랜드별 전체 메뉴(메뉴 분류·사양·옵션·가격 포함) 등록
- 원본 채팅 보존 (분석 실패·브랜드 변경 시에도 유지)
- 주문 이벤트 처리: 추가(ADD)·수정(UPDATE)·취소(CANCEL)·확정(CONFIRM)·무관(IGNORE)
- 선택한 브랜드의 메뉴·옵션·가격 기준 정규화와 검증. 모호한 주문은 임의 확정하지 않고 확인 요청
- 확인 필요 항목 우선 표시, 개별 항목 수정과 해당 주문만 재검증
- 개인 확인: 주문자별 만료형 무작위 토큰 링크, 확인 완료·수정 요청, 내용 변경 시 재확인
- 브랜드 변경 정책: 분석 후 변경 시 결과 무효화·재분석, 개인 확인 후 변경 시 확인 상태 취소·재확인, 확정 후에는 새 주문 버전으로 진행
- 확정 조건 충족 시에만 최종 확정, 확정 버전 고정
- 매장 주문서, 개인별 정산 내역, 주문 처리 결과 생성 (CSV 다운로드, 인쇄용 화면)
- 주요 화면: 주문 시작, 분석·검토, 개인 확인, 확인 현황, 주문 완료
- 사용자에게는 기술 오류 대신 이해하기 쉬운 진행 상태·안내 문구 표시
- 공통 주문 구조(카테고리 → 브랜드 → 상품 → 사양·옵션 → 주문)는 확장 가능하게 설계하되 카페만 구현
- 작업 상태·체크포인트 저장과 동일 Snapshot 중복 방지
- 모의 의존 서비스 기반 장애 주입과 Auto Healing 워크플로 (탐지·진단·복구·독립 검증·에스컬레이션)
- CI/CD: 자동 테스트, 필수 테스트 실패 시 배포 차단, 배포 결과 알림
- 검증 지표(MTTD·MTTR 등)와 사건 로그 기록

### 제외 범위

- 카페 외 카테고리(치킨·피자·햄버거)의 실제 주문 기능, 브랜드·매장 메뉴 자동 연동
- 메신저 실시간 연동과 개인 확인 링크 자동 발송 (담당자가 직접 복사·전달)
- 실제 매장 주문 전송·결제·송금·환불, 할인·쿠폰·세트 구성
- 회원가입·본인 인증, 메뉴 추천, 실시간 공동 편집, 고급 관리자 대시보드
- LLM이 생성한 명령의 자동 실행, 허용목록 밖 서비스 재시작, 실제 데이터 삭제, 운영 DB 변경, 비용 한도 없는 클라우드 리소스

### 사용할 환경

- [ ] 로컬 프로세스
- [ ] Docker Compose
- [ ] Kubernetes 로컬 클러스터
- [x] 클라우드 샌드박스 — AWS EC2 등 클라우드에 배포 예정 (비용 한도 [미결정])
- [ ] 기타:

> 장애 주입은 실습 전용 인스턴스 안에서만 수행하며, 비용 한도 없는 리소스 확장은 하지 않는다.

### 선택한 장애 유형

- [x] HTTP 5xx
- [x] 타임아웃
- [x] 프로세스 중단
- [ ] 잘못된 설정
- [ ] 의존 서비스 연결 실패 — 메뉴 저장소 조회 실패, 선택 항목
- [x] 반복 장애
- [x] 기타: 잘못된 에이전트 출력(스키마 위반) — 업무 층 에이전트화로 필수 승격

> 기획안의 "확인 후 데이터 변경 → 재확인", "정산 오류 → 확정 데이터 기준 재계산", "동일 채팅 재입력 → 중복 방지"는 장애가 아니라 업무 규칙·데이터 무결성 요구사항으로 다룬다.

# 2. 에이전트 설계

> 역할은 개념 수준으로 정의하고 과설계를 피한다.
>
> **구현 형태:** 업무 층은 Intake Agent·Menu Agent(LLM, Menu는 메뉴 조회 도구 사용), Validation(규칙 + 모호 항목 LLM 보조 검토), Settlement(계산 규칙)로 구성한다. 장애 대응 층은 모두 규칙·상태기계로 구성한다. LLM 출력은 스키마 검증을 통과해야 다음 단계로 전달되며, 메뉴 존재·가격·합계·상태 전이는 규칙으로 최종 판정한다.
>
> 업무 층(주문 이벤트 추출·브랜드 메뉴 정규화·주문 검증·정산)은 **보호 대상 서비스**이고, 아래 역할은 그 서비스를 복구하는 **장애 대응 층**이다. 업무 층의 "주문 검증"과 장애 대응 층의 "복구 검증(Verification)"은 서로 다른 역할이다.

## 2.1 장애를 탐지하는 주체는 누구인가?

**에이전트 이름:** Monitor

**관찰 데이터:**

- [x] 헬스체크 응답
- [x] 애플리케이션 로그
- [x] 오류율
- [x] 응답시간
- [x] 프로세스 상태
- [x] 기타: 작업 상태 정체(RUNNING 상태가 제한시간 이상 유지)

**장애 판정 조건:** 헬스체크 5초 주기, 연속 2회 실패 시 장애로 판정. 의존 서비스 5xx 응답, 호출 제한시간(5초) 초과, 프로세스 응답 없음, RUNNING 상태에서 체크포인트가 60초 이상 갱신되지 않는 작업 정체

**출력 메시지:** 사건(incident) 생성 — 사건 ID, 대상 서비스, 관찰 신호, 탐지 근거, 탐지 시각

---

## 2.2 원인을 진단하는 주체는 누구인가?

**에이전트 이름:** Diagnosis

**입력:** Monitor가 생성한 사건과 탐지 근거, 최근 로그·상태 조회 결과, 과거 시도 이력

**분류할 장애 유형:**

| 장애 코드 | 설명 | 판단 근거 | 신뢰도 또는 규칙 |
|---|---|---|---|
| DEP_HTTP_5XX | 주문 해석 서비스의 일시적 5xx | 응답 코드 5xx | 규칙 기반 |
| DEP_TIMEOUT | 주문 해석 서비스 응답 지연·타임아웃 | 제한시간 초과 | 규칙 기반 |
| WORKER_DOWN | 주문 처리 프로세스 중단 | 프로세스 상태 비정상, 작업 상태 정체 | 규칙 기반 |
| AGENT_OUTPUT_INVALID | 업무 에이전트 출력 스키마 위반 | 스키마 검증 실패 기록 | 규칙 기반 |
| REPEATED_FAILURE | 동일 장애 반복 | 동일 장애 코드의 연속 발생 횟수 | 규칙 기반 (회로 차단 조건과 연동) |
| UNKNOWN | 위 규칙에 해당하지 않음 | 분류 불가 | — |

**원인을 판단할 수 없을 때 행동:** UNKNOWN으로 분류하고 자동 변경 없이 사람에게 에스컬레이션한다.

## 2.3 복구를 실행하는 주체는 누구인가?

**에이전트 이름:** Recovery

**허용된 복구 행동:**

- 제한된 재시도와 지수 백오프 (의존 서비스 호출)
- 사전에 승인된 대체 주문 해석 서비스로 전환
- 테스트 환경의 허용목록에 있는 주문 처리 프로세스 재시작
- 마지막 성공 체크포인트부터 작업 재개 (같은 작업의 동시 재실행 방지 포함)

**금지된 행동:**

- LLM이 생성한 임의 명령 실행
- 허용목록 밖 서비스 재시작
- 주문·확인·정산 데이터 삭제 또는 임의 수정, 확정된 주문 버전 덮어쓰기
- 재시도 상한·회로 차단 우회

**필요한 도구·API·명령:** 개념 수준만 정의 — 의존 서비스 재호출, 대체 서비스 전환, 허용목록 기반 프로세스 재시작, 체크포인트 조회·재개. 구체 명령은 PRD 이후 단계에서 정의

---

## 2.4 복구 성공을 독립적으로 검증하는 주체는 누구인가?

**에이전트 이름:** Verification

**독립성이 필요한 이유:** Recovery의 "성공" 보고만으로는 실제 정상화와 주문 데이터 무결성(중복·유실 없음, 개인 확인 상태 보존)을 보장할 수 없다. 복구를 실행한 주체와 다른 주체가 측정값으로 판정해야 한다.

**검증 항목:**

- [x] 헬스체크 정상
- [x] 핵심 기능 테스트 통과 (기준 채팅 + 기준 브랜드 입력 → 주문 분석·정산 생성)
- [x] 오류율 정상 범위
- [x] 응답시간 정상 범위
- [x] 데이터 무결성 확인 (주문 중복·유실 0건, 개인 확인 상태 보존, 개인별 합계 = 전체 금액)
- [x] 회귀 테스트 통과

**복구 실패 판정 조건:** 위 항목 중 하나라도 기준 미달이면 복구 실패로 판정한다. 각 항목의 수치 기준은 5.1 참조

## 2.5 오케스트레이터가 필요한가?

- [x] 필요함
- [ ] 필요하지 않음

**판단 근거:** 탐지 → 진단 → 복구 → 검증 순서, 사건별 시도 횟수, 회로 차단 상태, 전체 워크플로 타임아웃을 한곳에서 관리해야 무한 복구 루프와 동시 재실행을 막을 수 있다.

### 오케스트레이터의 책임

- 역할 호출 순서와 사건 상태 관리
- 사건별 시도 횟수 기록과 재시도 상한·회로 차단 적용
- 전체 워크플로 타임아웃 관리와 에스컬레이션 결정

### 오케스트레이터가 해서는 안 되는 일

- 재시도 상한·회로 차단·권한 제한 우회
- 서비스·데이터를 직접 조작하는 복구 실행

## 2.6 에이전트 협업 구조

| 에이전트 | 입력 | 출력 | 호출 주체 | 허용 권한 | 타임아웃 |
|---|---|---|---|---|---:|
| Monitor | 헬스체크·로그·지표·작업 상태 | 사건 생성 | 주기 실행 | 조회, 사건 생성 | [미결정] |
| Diagnosis | 사건, 증거, 시도 이력 | 장애 코드, 근거, 추천 복구 | Orchestrator | 증거 조회, 복구안 제안 | [미결정] |
| Recovery | 승인된 복구 전략 | 복구 수행 결과 | Orchestrator | 허용목록 내 재시도·대체 전환·재시작·재개 | [미결정] |
| Verification | 사건, 복구 결과 | 정상화 판정과 근거 | Orchestrator | 헬스체크·기능 검증 조회 | [미결정] |
| Notification | 최종 상태, 증거, 추천 행동 | 화면 승인 요청 표시, 외부 메신저 알림 | Orchestrator | 보고, 승인 요청 | [미결정] |

### 협업 흐름

```text
[장애 발생]
  ↓
[Monitor — 신호 관찰, 사건 생성]
  ↓
[Orchestrator — 시도 횟수·회로 상태 확인]
  ↓
[Diagnosis — 장애 유형 분류 (UNKNOWN이면 에스컬레이션)]
  ↓
[Recovery — 허용된 복구 실행]
  ↓
[Verification — 독립 검증]
  ├─ 성공 → [사건 종료, 지표·로그 기록]
  └─ 실패 → [상한 내 재시도 / 상한·회로 차단 시 상태 보존 후 Notification으로 에스컬레이션]
```

> 사용자 화면에는 장애 대응 역할의 기술 정보 대신 "주문 내역은 저장되어 있어요. 중단된 작업을 다시 진행합니다."와 같은 안내만 표시한다. 상세 정보는 운영자 화면과 로그에 남긴다.

# 3. 자율성과 통제

## 3.1 자동으로 실행해도 되는 복구는 무엇인가?

| 복구 행동 | 자동 허용 이유 | 영향 범위 | 선행조건 | 실행 후 검증 |
|---|---|---|---|---|
| 의존 서비스 호출 재시도 (지수 백오프) | 일시적 장애에 효과적이고 데이터를 바꾸지 않음 | 해당 요청 | 시도 상한 이내, 회로 닫힘 | 해당 단계 성공 + Verification |
| 대체 주문 해석 서비스 전환 | 사전에 승인된 대체 서비스만 사용 | 해당 요청 | 1차 서비스 재시도 상한 초과, 대체 서비스 헬스체크 정상 | 기능 테스트 + 1차 서비스 정상화 시 기존 경로 복원 |
| 허용목록 내 처리 프로세스 재시작 | 테스트 환경이고 대상이 사전 지정됨 | 주문 처리 프로세스 | 허용목록 포함, 시도 상한 이내 | 헬스체크 + 핵심 기능 테스트 |
| 체크포인트부터 작업 재개 | 저장된 상태 기준이라 처음부터 재처리하지 않음 | 미완료 작업 | 체크포인트 존재, 같은 작업 미실행 중 | 중복·유실 0건, 개인 확인 상태 보존 확인 |

## 3.2 사람의 승인이 필요한 복구는 무엇인가?

| 복구 행동 | 승인 필요 이유 | 승인자 | 승인 타임아웃 | 미승인 시 행동 |
|---|---|---|---:|---|
| 설정 변경 | 서비스 동작이 바뀜 | 운영자 (화면에서 승인) | 10분 | 변경하지 않고 FAILED 상태 보존, 재알림 |
| 회로 차단 후 자동 복구 재개 | 반복 장애의 원인이 해결됐는지 사람이 판단해야 함 | 운영자 (화면에서 승인) | 10분 | 회로 열림 유지, 재알림 |
| 원인 불명(UNKNOWN) 장애 조치 | 자동 판단 근거 없음 | 운영자 (화면에서 승인) | 10분 | 자동 변경 없이 대기, 재알림 |

> 재알림: 10분 간격, 최대 3회

> 승인 요청은 화면에 표시하고 운영자가 화면에서 승인·거부한다. 알림은 외부 메신저 알림으로 보낸다.
>
> 업무 승인: 개인별 주문 확인은 주문 참여자가, 최종 확정은 주문 담당자가 수행한다. 이는 복구 승인과 별개의 업무 흐름이다. 최종 확정 조건은 검증 완료, 미해결 확인 항목 0건, 변경·취소 이력 반영, 전원 개인 확인 완료, 개인별 합계와 전체 금액 일치이다.

## 3.3 복구를 몇 번까지 재시도할 것인가?

> 아래 수치는 근거를 붙인 초안을 우선 확정한 값이며, 실험 결과에 따라 수정할 수 있다.

**최대 시도 횟수:** 1차 주문 해석 서비스 최대 3회 → 대체 서비스 1회 전환 후 최대 2회. 프로세스 재시작은 10분 안에 최대 2회

**호출 제한시간:** 5초 (모의 응답 기준. 실제 LLM 연결 시 재조정)

**대기 방식:**

- [ ] 고정 대기
- [ ] 선형 증가
- [x] 지수 백오프
- [ ] 지수 백오프 + 무작위 지연

**대기시간:** 1초 → 2초 → 4초 (무작위 지연 없음 — 호출 주체가 하나이고 측정 재현성을 우선)

**시도 횟수를 저장할 위치:** 영속 상태 저장소(사건 기록). 프로세스가 재시작되어도 횟수가 유지되어야 한다.

# 5. 검증

## 5.1 복구 성공을 어떤 지표로 판정할 것인가?

| 지표 | 정상 기준 | 측정 위치 | 실패 기준 |
|---|---|---|---|
| 헬스체크 | 2초 간격 연속 3회 정상 | Verification | 정상 응답 미달 |

> 업무 품질 지표(장애 복구와 별도): 주문 추출·수정·취소 정확도, 브랜드 메뉴·옵션 매칭 정확도, 등록되지 않은 옵션의 자동 확정 0건, 최종 금액 불일치 0건. 목표 수치는 [미결정]

## 5.2 장애 탐지부터 복구까지 걸린 시간을 어떻게 측정할 것인가?

```text
injected_at          = 장애 주입 시각 (장애 주입기 기록)
detected_at          = Monitor 사건 생성 시각
recovery_started_at  = Recovery 첫 복구 시작 시각
recovered_at         = Verification 정상 판정 시각
```

```text
MTTD = detected_at - injected_at
MTTR = recovered_at - injected_at
복구 실행시간 = recovered_at - recovery_started_at
```

**시간을 기록할 컴포넌트:** 장애 주입기, Monitor, Recovery, Verification (각자 자기 시각만 기록)

**시간 형식과 타임존:** 저장은 UTC·ISO 8601·밀리초, 화면 표시는 KST

**목표:** MTTD 15초 이하, MTTR 5xx·타임아웃 60초 이하·프로세스 중단 90초 이하, 복구 가능 장애 3종 각 5회 반복 시 복구 성공률 80% 이상 (데이터 무결성은 100%)

# 7. 최종 범위 선언

## 반드시 구현할 것

1. 채팅·브랜드 입력 → 주문 분석·검증 → 담당자 검토 → 개인 확인 → 최종 확정 → 주문서·개인별 정산 생성의 정상 흐름
2. 상태·체크포인트 저장, 동일 Snapshot 중복 방지, 확정 버전 고정
3. 모의 의존 서비스 기반 장애 4종(5xx, 타임아웃, 프로세스 중단, 반복 장애) 주입과 탐지·진단·복구·독립 검증·에스컬레이션
4. CI/CD: 자동 테스트와 필수 테스트 실패 시 배포 차단

## 구현하지 않을 것

1. 카페 외 카테고리의 실제 주문, 브랜드·매장 메뉴 자동 연동
2. 메신저 실시간 연동·링크 자동 발송, 실제 주문 전송·결제·송금, 회원가입·본인 인증
3. LLM 생성 명령 자동 실행, 허용목록 밖 재시작, 비용 한도 없는 클라우드 리소스

## 성공 기준

1. 지정된 장애 시나리오별로 자동 복구 성공 여부를 판정하고, injected_at·detected_at·recovered_at을 기록해 MTTD·MTTR을 산출할 수 있다.
2. 복구 후 기준 채팅·브랜드 입력의 주문 수량·정산이 정답 데이터와 100% 일치하고, 주문 중복·유실 0건, 개인 확인 상태가 보존된다.
3. 반복 장애에서 회로가 차단되고, 자동 복구 실패 시 상태를 보존한 채 사람에게 에스컬레이션된다.
4. 필수 테스트를 의도적으로 실패시키면 배포가 100% 차단된다.
