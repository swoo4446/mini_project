## 2. 프로젝트 개요

WorkGuide AI는 매뉴얼, 정책, 경영자료, 업무자료 같은 사내 자료를 한곳에 모은 아카이브다. 사용자는 이 아카이브를 기반으로 질의할 수 있다.

- 사용자의 권한 등급 안에서만 자료를 검색한다.
- 실제 LLM으로 근거 기반 답변을 만든다.
- 원문과 대조해 날짜·금액·조건이 빠지거나 틀리지 않았는지 검증한다.
- 절차를 묻는 질문에는 실행 체크리스트까지 제공한다.

이 프로젝트의 핵심은 질의 기능 자체가 아니라 **서비스 운영 중 발생하는 장애를 자동으로 탐지·진단·복구하고, 복구 결과를 독립적으로 검증하는 멀티 에이전트 워크플로**다. 다섯 가지 장애를 다룬다.

- LLM API 오류·응답 지연
- 프롬프트·출력 오류
- DB 연결 실패
- Worker 컨테이너 종료
- 문서 검색 장애

복구는 안전 원칙을 따른다. 권한을 완화하지 않고, 검증되지 않은 근거나 근거 없는 답변을 내보내지 않으며, 시도와 비용에 상한을 둔다.

**한 문장 정의**

> 사용자가 사내 자료에 대한 질문을 요청하면, 서비스는 권한 등급 안에서 매뉴얼·정책·경영자료·업무자료 아카이브를 검색하고 실제 LLM으로 답변을 생성·검증한 뒤, 근거 문서와 인용 위치가 포함된 답변(절차형 질문은 실행 체크리스트 포함)을 반환한다.

**최종 형태와 MVP의 관계**

최종 형태는 사용자가 자료를 직접 올리면 자동으로 파싱해 아카이브에 넣는 서비스다. 3일 MVP에서는 미리 정리한 가상 문서를 메타데이터와 함께 적재하는 방식으로 진행한다. 업로드·자동 파싱 경로가 나중에 같은 메타데이터 구조로 들어올 수 있도록 설계한다 (FR-001).

## 3. 문제 정의

### 3.1 사용자 문제

- 매뉴얼, 정책, 경영자료, 업무자료가 여러 곳에 흩어져 있어 필요한 정보를 찾기 어렵다.
- 규정과 절차의 용어가 어렵다. 신청 조건, 기한, 준비물을 직접 정리해야 한다.
- 일반 검색이나 RAG 챗봇은 권한 차이를 반영하지 못한다. 또 날짜·금액·조건을 빠뜨리거나 잘못 전달할 수 있다.

### 3.2 운영 문제

- 서비스가 LLM API, 문서 검색, DB, 여러 실행 프로세스에 의존하므로 한 구성요소만 실패해도 전체 응답이 실패한다.
- 지금은 사람이 장애를 발견하고 대응한다. 사용자 제보나 로그로 장애를 알아채고, 로그를 직접 읽어 원인을 판단하고, 수동으로 재시작한 뒤 요청을 처음부터 다시 보낸다.
  - 탐지가 늦다.
  - 판단 근거가 기록되지 않는다.
  - 처음부터 다시 처리하므로 LLM 호출이 중복되고 비용이 늘어난다.
  - 복구했는지 눈으로만 확인한다.
- 복구를 서두르다 권한 필터를 건너뛰면 하위 등급 사용자에게 경영자료가 노출될 수 있다. 검증되지 않은 정보를 내보내면 장애보다 더 큰 보안·정확성 문제가 생긴다.

### 3.3 서비스 경계

| 포함 | 경계 밖 |
|---|---|
| 자료 적재와 아카이브, 질의 API, 업무 처리 에이전트, 문서 검색 서비스, 문서·상태 저장소, 검증된 캐시, 장애 대응 워크플로, 장애 주입 계층, 배포 구성, 파이프라인, 알림 | 실제 사내 시스템·SSO·조직도, 문서 자동 신청·결재, 실제 기업 데이터 |

### 3.4 중단 영향과 심각도

- **사용자:** 답변을 받지 못하거나 응답이 늦어진다. 근거나 날짜·금액·조건이 빠진 잘못된 답변을 받을 수 있다.
- **운영:** 수동 로그 분석, 재시작, 요청 재전송을 해야 한다. 담당자가 지정되어 있지 않다.
- **데이터·비용·보안:** 가상 데이터라 실제 피해는 없다. 대신 LLM 비용이 늘어날 수 있고, API 키가 노출될 수 있고, 복구 중 경영자료가 노출될 수 있다.
- **심각도:** 중간

## 7. 정상 서비스 시나리오

### 7.1 정상 흐름

```text
사용자 (권한 등급 + 질문)
  → 질의 API: 요청 ID 발급
  → Policy Guard: 서버 측 권한 확인, 검색 가능 범위 결정
  → Planner: 질문 유형 분류, 실행 경로 선택
  → Retrieval: 허용 범위 안에서 문서 검색, 관련 조항·인용 위치 수집
  → Explanation: 쉬운 설명, 행동 항목·체크리스트 작성
  → Critic: 원문 대비 날짜·금액·조건·준비물·근거 검증
      (실패 시 누락 항목을 Explanation에 전달해 수정, 최대 2회)
  → 응답: 답변 + 근거 문서 ID·인용 위치 (+ 절차형이면 체크리스트)
  (각 단계의 결과는 Memory Keeper가 Handoff 상태와 체크포인트로 저장)
```

### 7.2 예시

- **질문:** "나는 영업팀 직원인데, 이번에 지방 출장을 다녀왔어. 출장비를 정산하려면 어떻게 해야 해?"
- **결과 (가상 규정 기준):**
  - 출장 결과보고서 작성
  - 교통비·숙박비 영수증 첨부
  - 정산 마감일 확인
  - 경비 시스템에서 정산 신청
  - 근거: 출장관리 규정 제4조, 경비 정산 매뉴얼 3장

### 7.3 질문 유형과 실행 경로

| 질문 유형 | 실행 경로 | 출력 |
|---|---|---|
| 절차형 | Policy Guard → Planner → Retrieval → Explanation → Critic | 설명 + 실행 체크리스트 + 근거 |
| 정보형 | Policy Guard → Planner → Retrieval → Explanation → Critic | 요약 답변 + 근거 |
| 여러 문서에 걸친 질문 | Policy Guard → Planner → Retrieval(여러 문서) → Explanation → Critic | 문서별 근거를 구분한 답변 |
| 권한 밖 요청 | Policy Guard → 차단 (LLM 호출 없음) | BLOCKED, 정보 노출 없음 |
| 근거 부족 | Retrieval → Critic → 응답 보류 | 근거 부족 안내 |

## 8. 장애 시나리오

| ID | 장애 | 발생 위치 | 탐지 가능한 신호 | 사용자·운영 영향 | 안전한 재현 방법 |
|---|---|---|---|---|---|
| F1 | LLM API 오류·응답 지연 (5xx, 429, 10초 초과) | 기본 모델 호출 | 상태 코드 분포, 지연시간, 타임아웃 수 | 응답 실패·지연 | 장애 주입 계층이 기본 모델 호출에 오류·지연을 강제 |
| F2 | 프롬프트·출력 오류 (잘못된 JSON 구조, 필수 조건·근거 누락) | LLM 응답 | 구조 검증 실패, Critic 검증 실패 | 잘못되거나 불완전한 답변 | 장애 주입 계층이 구조가 깨지거나 필수 조건이 빠진 응답 반환 |
| F3 | DB 연결 실패 | 문서·상태 저장소 | 연결 오류, DB 헬스체크 실패 | 상태 저장·조회 불가 | 실험 중 DB 연결을 일시 차단 |
| F4 | 작업 중 Worker 컨테이너 종료 | 에이전트 실행 Worker | 헬스체크 실패, 실행 상태 중단 | 처리 중 요청 중단 | 처리 중 테스트용 Worker 강제 종료 |
| F5 | 문서 검색 장애 | 문서 검색 서비스 | 검색 오류 응답, 연결 실패, 타임아웃 | 근거 수집 불가 | 실험 중 검색 서비스 오류·연결 차단 |
| R | 반복 장애·복구 불가 (공통 정책) | F1 등을 지속 | 같은 유형의 연속 실패 | 자동 복구 불가 | F1을 기본·대체 모델 모두에 지속 |
| S1 | 권한 외 자료 요청 (보안 검증) | Policy Guard | 권한 불일치 | 경영자료 노출 위험 | 일반 직원 등급으로 경영자료 질문 |

- 장애 주입 계층은 테스트 환경에서만 켠다. 실제 LLM 제공사에 비정상 트래픽을 보내지 않는다.
- R과 S1은 수동 개입 없는 복구 비율 계산에서 제외한다.

## 9. 멀티 에이전트 구성

### 9.1 구조 선택 근거

이 서비스는 **업무 처리 계층**과 **장애 대응 계층**으로 나눈다.

- **응답 속도:** Planner가 질문 유형에 따라 필요한 단계만 실행한다. 권한 밖 요청은 LLM 호출 없이 차단한다.
- **결정 일관성:** 권한 판단은 LLM에 맡기지 않고 백엔드 규칙(Policy Guard)이 먼저 한다. Retrieval은 허용된 문서만 검색한다. Critic이 원문과 날짜·금액·조건을 대조한다.
- **장애 격리:** 업무 처리와 장애 대응을 분리한다. 실패한 단계는 체크포인트부터 재개한다. 회로 차단으로 장애가 다른 요청에 번지지 않게 한다.
- **과설계 방지:** 규칙으로 충분한 역할은 LLM 에이전트로 만들지 않는다. Policy Guard, Memory Keeper, 장애 대응 역할이 여기에 해당한다. 장애 대응 역할에 LLM을 쓸지는 [미결정]이다 (U-08).
- **역할 구분:**
  - 업무 처리 순서는 Planner가, 장애 대응 순서는 Orchestrator가 관리한다.
  - 답변 내용 검증은 Critic이, 복구 후 정상화 검증은 Verification이 한다.
  - 기획서의 Recovery Controller는 Monitor, Diagnosis, Recovery, Verification, Orchestrator, Notification으로 나눴다.

| 계층 | 구성요소 | 구현 성격 |
|---|---|---|
| 업무 처리 | Planner, Retrieval, Explanation, Critic | LLM 사용 에이전트 |
| 업무 처리 | Policy Guard, Memory Keeper | 프로그램 로직 |
| 장애 대응 | Monitor, Diagnosis, Recovery, Verification, Orchestrator, Notification | 규칙·상태기계 중심 |

### 9.2 업무 처리 에이전트

#### Policy Guard

- **책임:** 서버 측 권한 등급 확인, 검색 가능 문서 범위 결정
- **입력:** 요청 ID, 사용자 권한 등급
- **출력:** 허용 문서 범위 또는 차단 결정
- **사용할 수 있는 정보:** 문서 메타데이터(접근 가능 등급, 시행일)
- **허용 행동:** 권한 판정, 차단
- **금지 행동:** 사용자가 제출한 권한 정보를 검증 없이 신뢰하기, 복구를 이유로 권한 완화하기
- **실패 시 행동:** 판정할 수 없으면 차단(BLOCKED)한다. 허용 쪽으로 처리하지 않는다.

#### Planner

- **책임:** 질문 의도·유형 분류(7.3), 실행 경로 선택
- **입력:** 질문, 검증된 권한 등급
- **출력:** 실행 계획 (질문 유형, 실행할 단계)
- **사용할 수 있는 정보:** 질문, 자료 유형 목록
- **허용 행동:** 분류, 경로 선택
- **금지 행동:** 권한 판단, 답변 내용 생성
- **실패 시 행동:** 분류할 수 없으면 근거 부족 경로로 보낸다. LLM 호출이 실패하면 사건을 생성한다.

#### Retrieval

- **책임:** 허용 범위 안에서 문서 검색, 관련 조항 추출, 근거 연결
- **입력:** 실행 계획, 허용 문서 범위
- **출력:** 문서 ID, 버전, 인용 위치, 원문 발췌
- **사용할 수 있는 정보:** 허용 범위의 문서와 메타데이터
- **허용 행동:** 검색, 근거 수집
- **금지 행동:** 권한 밖 문서 검색, 적용 기간이 지난 버전을 현재 규정으로 제시하기
- **실패 시 행동:** 검색 서비스 오류는 F5 사건으로 생성한다. 결과가 없으면 근거 부족으로 처리한다.

#### Explanation

- **책임:** 쉬운 설명, 행동 항목·체크리스트 작성
- **입력:** 검색 근거, 질문 유형, Critic의 수정 요청(누락 항목)
- **출력:** 정해진 구조의 답변 초안
- **사용할 수 있는 정보:** Retrieval이 넘긴 근거
- **허용 행동:** LLM을 이용한 답변 생성·수정
- **금지 행동:** 근거에 없는 내용 생성
- **실패 시 행동:** LLM 오류는 F1 사건으로, 구조 오류는 F2 사건으로 생성한다.

#### Critic

- **책임:** 원문 대비 날짜·금액·조건·준비물·근거 검증
- **입력:** 답변 초안, 원문 근거
- **출력:** 통과 / 수정 요청(누락·불일치 항목 포함) / 보류
- **사용할 수 있는 정보:** 초안, 원문 근거
- **허용 행동:** 비교·판정, 수정 요청
- **금지 행동:** 근거 없이 통과 처리, 내용을 직접 고쳐 통과시키기
- **실패 시 행동:** 수정 루프가 2회를 넘으면 F2 사건을 생성하고 응답을 보류한다.

#### Memory Keeper

- **책임:** Handoff 상태, 중간 결과, 체크포인트, 시도 이력 보관
- **입력:** 각 단계의 출력
- **출력:** 저장된 상태, 재개 지점
- **사용할 수 있는 정보:** 요청별 실행 상태
- **허용 행동:** 저장, 조회, 필수 필드 확인
- **금지 행동:** 검증되지 않은 상태를 재개 지점으로 제공하기, 상태 임의 수정
- **실패 시 행동:** 저장소에 접근할 수 없으면 F3 사건을 생성한다.

### 9.3 장애 대응 에이전트

#### Monitor

- **책임:** 유형별 메트릭 관찰, 사건 생성
- **입력:** 헬스체크, 로그, 유형별 메트릭(10.3)
- **출력:** 사건 정보 (사건 ID, 요청 ID, 대상, 감지 범주, 신호, 탐지 시각, 증거)
- **사용할 수 있는 정보:** 메트릭, 로그, 컨테이너 상태
- **허용 행동:** 조회, 사건 생성
- **금지 행동:** 설정 변경, 복구 실행
- **실패 시 행동:** Monitor 자신의 헬스체크가 실패하면 플랫폼 재시작 정책을 따르고 알림을 보낸다.

#### Diagnosis

- **책임:** 장애 코드 분류와 권장 복구전략 제시
- **입력:** 사건 정보, 증거, 시도 이력
- **출력:** 장애 코드(F1~F5, REPEATED, UNKNOWN), 근거, 권장 전략
- **사용할 수 있는 정보:** 사건, 로그, 시도 이력
- **허용 행동:** 증거 조회, 복구안 제안
- **금지 행동:** 복구 직접 실행, 원인 추측
- **실패 시 행동:** 분류할 수 없으면 UNKNOWN으로 판정해 에스컬레이션한다.

#### Recovery

- **책임:** 승인된 복구전략 실행
- **입력:** 장애 코드, Orchestrator가 승인한 전략
- **출력:** 수행 결과 (행동, 시도 횟수, 결과)
- **사용할 수 있는 정보:** 허용목록, 체크포인트, 검증된 캐시
- **허용 행동:** 재시도, 대체 모델 전환, 재생성, 재연결, 허용목록 Worker 재시작, 체크포인트 재개, 검증된 캐시 폴백
- **금지 행동:** 권한 완화, 검증되지 않은 문서·캐시 사용, 근거 없는 답변 내보내기, 임의 명령 실행, 허용목록 밖 재시작, 데이터 삭제, 비용 상한 초과 호출, 스스로 복구 완료 선언
- **실패 시 행동:** 실패 결과를 Orchestrator에 보고한다. 다음 전략 선택은 Orchestrator가 한다.

#### Verification

- **책임:** 복구 후 서비스 정상화를 독립적으로 검증
- **입력:** 사건 정보, 복구 수행 결과
- **출력:** 검증 결과 (통과/실패, 항목별 근거)
- **사용할 수 있는 정보:** 헬스체크, 기준 질문 세트, 문서 메타데이터
- **허용 행동:** 헬스체크, 기준 질문 재처리, 근거·권한·단계 중복 확인
- **금지 행동:** 검증 없이 통과 처리, 복구 행동 실행
- **실패 시 행동:** 검증할 수 없으면 실패로 판정한다.

#### Orchestrator

- **책임:** 사건 상태 관리, 장애 대응 역할 호출 순서, 시도·회로·비용·시간 상한 적용
- **입력:** 각 장애 대응 역할의 출력
- **출력:** 사건 상태 전이, 다음 역할 호출, 에스컬레이션 요청
- **사용할 수 있는 정보:** 사건 상태, 시도 이력, 정책 설정
- **허용 행동:** 역할 호출, 회로 열기·닫기, 에스컬레이션
- **금지 행동:** 상한·회로·권한 정책 우회, 서비스·데이터 직접 조작
- **실패 시 행동:** 전체 워크플로 제한시간(2분)을 넘기면 FAILED로 처리하고 에스컬레이션한다.

#### Notification

- **책임:** 사건 결과와 파이프라인 결과를 알리고 담당자 할당
- **입력:** 최종 사건 상태, 증거, 권장 조치, 파이프라인 결과
- **출력:** 알림 메시지, 담당자 할당, 에스컬레이션 기록
- **사용할 수 있는 정보:** 담당자 매핑, 사건 요약
- **허용 행동:** 알림 발송, 승인·확인 요청
- **금지 행동:** 복구 정책 변경, 민감정보 포함 발송
- **실패 시 행동:** 발송에 실패하면 로컬 기록을 남기고 재발송한다 (최대 3회).

## 10. 에이전트 협업 흐름

### 10.1 장애 대응 흐름

```text
[장애 발생]
  ↓
Monitor: 유형별 메트릭 관찰 → 사건 생성
  ↓
Orchestrator: 사건 등록, 시도 횟수·회로·비용 상한 확인
  ↓
Diagnosis: 장애 코드 분류 (F1~F5 / REPEATED / UNKNOWN)
  ↓
Recovery: 승인된 복구전략 실행
  ↓
Verification: 독립 검증
  ├─ 통과 → RECOVERED 또는 DEGRADED → Notification이 결과 알림
  └─ 실패 → 상한 내면 다음 전략
            / 상한 초과·UNKNOWN → 회로 열기, 근거 없는 답변 차단 → Notification이 담당자 에스컬레이션
```

### 10.2 Handoff 상태

다음 상태를 단계 사이에 넘기고 Memory Keeper가 보관한다.

- 요청 ID, 질문
- 서버에서 검증한 권한 등급
- 질문 유형, 적용 기준일
- 실행 계획, 현재 단계
- 검색 문서 ID·버전·인용 위치·원문 근거
- 추출된 핵심 조건 (날짜·금액·조건·준비물)
- 답변 초안, 검증 결과
- 수정 루프 횟수
- 오류 유형, 시도 횟수, 복구 상태

규칙은 다음과 같다.

- 필수 필드가 하나라도 빠지면 다음 단계로 넘기지 않는다. 누락은 F2 범주로 기록한다.
- 체크포인트에서 재개하기 전에 권한과 문서 유효성을 다시 확인한다.
- 실제 스키마는 상세 설계 단계에서 확정한다.

### 10.3 유형별 감지 메트릭

| 범주 | 메트릭 | 판정 조건 |
|---|---|---|
| 네트워크 | 서비스 간 연결 실패 수, 연결 타임아웃 | 연속 3회 실패 |
| DB | 연결 실패 수, 쿼리 오류율 | 연속 3회 실패 |
| API | LLM API·검색 서비스의 상태 코드 분포(5xx, 429), 오류율 | 오류 발생 시 재시도 대상. 연속 3회면 대체 경로 |
| LLM | 호출 지연시간, 타임아웃 수, 토큰·비용 사용량 | 10초 초과 시 타임아웃. 비용 상한은 [미결정] (U-02) |
| 프롬프트 | 출력 구조 오류율, 필수 조건·근거 누락률 | 검증 실패 1건 발생 시 |
| 컨테이너 | 헬스체크 실패, 재시작 횟수 | 연속 3회 실패 |

## 11. 장애별 복구정책

| 장애 | 탐지 신호 | 진단 근거 | 1차 복구 | 2차 복구 | 최대 시도 | 사람 승인 | 롤백 | 성공 검증 |
|---|---|---|---|---|---:|---|---|---|
| F1 LLM API 오류·응답 지연 | 오류율·지연 상승 | 5xx·429, 10초 초과 | 기본 모델 재시도 (백오프) | 대체 모델 전환 | 3 | 불필요 | 회로 재개 조건 충족 시 기본 경로 복원 | 기준 질문 처리, 구조·근거 검증 |
| F2 프롬프트·출력 오류 | 구조·Critic 검증 실패 | 잘못된 구조, 필수 조건·근거 누락 | 누락 항목 전달 재생성 | 대체 모델로 재생성, 실패 시 응답 보류 | 2 | 불필요 | 잘못된 출력 폐기, 마지막 유효 상태 유지 | 구조·근거·권한 검증 |
| F3 DB 연결 실패 | 연결 오류, 헬스체크 실패 | 연결 오류 코드 | 재연결 (백오프) | 체크포인트 재개, 실패 시 응답 보류 | 3 | 불필요 | 상태 변경 없음, 재개 실패 시 요청 보류 | DB 헬스체크, 상태 조회, 요청 완료 |
| F4 Worker 컨테이너 종료 | 헬스체크 실패, 실행 상태 중단 | 컨테이너 상태 | 허용목록 Worker 재시작 | 저장된 단계부터 재개 | 3 | 불필요 | 재시작 반복 중단, 에스컬레이션 | 헬스체크, 요청 완료, 단계 중복 0건 |
| F5 문서 검색 장애 | 검색 오류·연결 실패·타임아웃 | 검색 서비스 오류 | 재연결 (백오프) | 권한·버전 일치 캐시 폴백 (DEGRADED) | 3 | 불필요 | 캐시 검증 실패 시 응답 보류 | 검색 복구 시 정상 응답, 폴백 시 권한·버전 일치 |
| R 반복 장애·복구 불가 | 같은 유형 연속 실패 | 상한 초과, 대체 경로 실패 | 회로 열기, 근거 없는 답변 차단 | 담당자 에스컬레이션 | 해당 없음 | 필요 (회로 해제 시) | 회로 유지 | 회로 상태·에스컬레이션 기록 |

**공통 정책**

| 항목 | 값 |
|---|---|
| 재시도 | 전략당 최대 3회, 지수 백오프 1초 → 2초 → 4초 + 무작위 지연 |
| 답변 수정 루프 | Critic 검증 실패 시 최대 2회 |
| LLM 호출 타임아웃 | 10초 |
| 회로 차단 | 같은 구성요소 연속 3회 실패 시 열림. 30초 냉각 후 시험 요청 1건이 Verification을 통과하면 닫힘 |
| 같은 전략 반복 | 한 사건에서 상한에 도달한 전략은 다시 선택하지 않음 |
| 전체 복구 워크플로 제한시간 | 2분. 초과 시 FAILED와 에스컬레이션 |
| LLM 호출·비용 상한 | 요청별·일별 상한 적용. 수치는 [미결정] (U-02) |

> 쿠버네티스의 자동 재시작과 Recovery의 재시작이 어디서 나뉘는지는 [미결정]이다 (U-11). 어느 쪽이 재시작하든, 체크포인트 재개와 Verification 검증은 반드시 거친다.

## 12. 자율성과 Human-in-the-loop

### 12.1 자동 실행 가능

- 기본 모델 재시도, 대체 모델 전환
- 누락 항목 전달 재생성, 잘못된 구조 재생성 (최대 2회)
- DB·검색 서비스 재연결
- 허용목록 Worker 재시작
- 검증 통과한 체크포인트부터 재개
- 권한 등급·버전 재확인을 통과한 캐시로 폴백

### 12.2 사람 승인 후 실행

| 행동 | 이유 | 승인자 | 승인 타임아웃 | 미승인 시 |
|---|---|---|---:|---|
| 회로 해제 전 강제 재개 | 반복 장애 원인 해소를 사람이 판단 | 장애 유형별 담당자 | [미결정] (U-09) | 회로 유지 |
| 문서·메타데이터 수정, 권한 등급 변경 | 정확성·권한에 직접 영향 | 자료 관리 담당자 | [미결정] | 변경하지 않음 |
| 설정 변경 (타임아웃, 임계값, 모델 경로, 비용 상한) | 전체 요청·비용에 영향 | 담당자 | [미결정] | 기존 설정 유지 |
| 이전 버전으로 배포 롤백 | 서비스 전체에 영향 | 배포 담당자 | [미결정] | 현재 버전 유지, 에스컬레이션 |
| UNKNOWN 장애 조치 | 원인 불명 | 담당자 | [미결정] | 사건 보고서만 남김 |

### 12.3 자동 실행 금지

- 권한 완화, 검증되지 않은 문서·캐시 사용, 근거 없는 답변 제공
- LLM이 생성한 임의 명령 실행
- 허용목록 밖 컨테이너·서비스 재시작
- 문서·상태 데이터 삭제
- 비용 상한을 넘는 호출, 인증정보 변경

### 12.4 에스컬레이션

장애 유형별로 1차 담당자를 할당한다. 복구가 실패하면 2차 담당자에게 넘긴다.

| 장애 범주 | 1차 담당 영역 | 2차 담당 영역 |
|---|---|---|
| LLM·프롬프트 (F1, F2) | AI 담당 | 에이전트 통합 담당 |
| 검색·권한 (F5, S1 이상) | 데이터·검색 담당 | 백엔드 담당 |
| DB (F3) | 백엔드 담당 | 인프라 담당 |
| 컨테이너 (F4) | 인프라 담당 | 백엔드 담당 |
| 파이프라인 실패 | 인프라 담당 | 팀 리더 |
| UNKNOWN | 팀 리더 | — |

> 담당 영역에 팀원 5명을 어떻게 배정할지는 [미결정]이다 (U-04).

## 13. 기능 요구사항

### FR-001 자료 적재 (아카이브)

- **설명:** 미리 정리한 가상 문서를 공통 메타데이터와 함께 아카이브에 등록한다.
- **입력:** 문서 본문, 메타데이터
  - 문서 ID, 자료 유형(매뉴얼·정책·경영자료·업무자료)
  - 버전, 적용 시작일·종료일
  - 접근 가능 권한 등급
  - 출처, 조항·인용 위치 단위
- **기대 동작:** 메타데이터를 검사한 뒤 등록하고 검색 대상에 포함한다.
- **예외 상황:** 필수 메타데이터가 빠졌거나 권한 등급이 없으면 등록을 거부한다.
- **확장 고려:** 후속 단계의 업로드·자동 파싱 경로도 같은 메타데이터 구조로 등록할 수 있게 한다.
- **인수조건:** 가상 문서 10~12개가 모두 등록된다. 권한 등급이 없는 문서는 등록이 거부된다.

### FR-002 질의 접수

- **설명:** 사용자 질문을 받아 요청 ID를 발급한다.
- **입력:** 사용자 권한 등급 정보, 질문
- **기대 동작:** 고유한 요청 ID를 발급하고 이후 모든 로그와 상태에 연결한다.
- **예외 상황:** 질문이 비어 있거나 형식이 잘못되면 오류 응답을 보낸다. LLM은 호출하지 않는다.
- **인수조건:** 테스트 질문 20개의 모든 요청에 고유한 요청 ID가 기록된다.

### FR-003 서버 측 권한 확인 (Policy Guard)

- **설명:** 권한 등급으로 검색 가능한 문서 범위를 정한다.
- **입력:** 요청 ID, 권한 등급
- **기대 동작:** 허용 범위 밖의 문서는 검색 대상에서 뺀다. 권한 밖 요청은 차단한다.
- **예외 상황:** 권한을 판정할 수 없으면 차단한다.
- **인수조건:** S1 시나리오에서 BLOCKED가 반환되고, 응답과 로그에 경영자료 원문이 0건이다.

### FR-004 질문 분석과 실행 경로 선택 (Planner)

- **설명:** 질문 유형을 분류하고 7.3의 실행 경로를 정한다.
- **입력:** 질문, 검증된 권한 등급
- **기대 동작:** 실행 계획을 Handoff 상태에 기록한다.
- **예외 상황:** 분류할 수 없으면 근거 부족 경로로 보낸다.
- **인수조건:** 테스트 질문 20개에서 각 질문의 실행 경로가 기대 경로와 일치한다.

### FR-005 문서 검색과 근거 수집 (Retrieval)

- **설명:** 허용 범위 안에서 적용 기준일에 유효한 문서를 검색하고 관련 조항을 추출한다.
- **입력:** 실행 계획, 허용 문서 범위
- **기대 동작:** 문서 ID, 버전, 인용 위치, 원문 발췌를 반환한다.
- **예외 상황:** 결과가 없으면 근거 부족으로 처리한다. 검색 서비스 오류는 F5 사건으로 생성한다.
- **인수조건:** 반환된 문서는 모두 권한 범위 안에 있고 적용 기준일에 유효하다.

### FR-006 답변·체크리스트 생성 (Explanation)

- **설명:** 실제 LLM으로 질문 유형에 맞는 구조화된 답변을 만든다.
- **입력:** 검색 근거, 질문 유형, 수정 요청
- **기대 동작:**
  - 절차형 질문은 체크리스트를, 정보형 질문은 요약을 만든다.
  - 모든 답변에 근거 문서 ID와 인용 위치를 붙인다.
- **예외 상황:** LLM 오류는 F1 사건으로, 구조 오류는 F2 사건으로 생성한다.
- **인수조건:** 정상 질문의 응답이 모두 응답 구조를 만족한다.

### FR-007 답변 검증과 수정 루프 (Critic)

- **설명:** 답변의 날짜·금액·조건·준비물·근거가 원문과 일치하는지 검증한다.
- **입력:** 답변 초안, 원문 근거
- **기대 동작:** 통과, 수정 요청(누락·불일치 항목 포함), 보류 중 하나로 판정한다. 수정 요청은 최대 2회까지 Explanation에 되돌린다.
- **예외 상황:** 2회를 넘기거나 근거가 없으면 보류한다.
- **인수조건:**
  - 근거 ID가 빠졌거나 원문과 다른 날짜·금액을 넣은 테스트 응답이 통과되지 않는다.
  - 날짜·금액·조건 보존율이 95% 이상이다.

### FR-008 Handoff 상태와 체크포인트 (Memory Keeper)

- **설명:** 10.2의 Handoff 상태를 단계마다 저장하고 재개 지점을 제공한다.
- **입력:** 각 단계의 출력
- **기대 동작:** 필수 필드를 확인한 뒤 저장한다.
- **예외 상황:** 필수 필드가 빠지면 다음 단계로 넘기지 않는다.
- **인수조건:** Handoff 테스트에서 필수 필드 누락이 0건이다. F4 실험에서 중단 직전 단계부터 재개된다.

### FR-009 장애 감지와 사건 생성 (Monitor)

- **설명:** 10.3의 메트릭으로 장애를 감지하고 사건을 만든다.
- **입력:** 메트릭, 헬스체크, 로그
- **기대 동작:** 사건 정보를 만들고 detected_at을 기록한다.
- **예외 상황:** 같은 장애로 사건이 중복 생성되지 않도록 묶는다.
- **인수조건:** F1~F5 실험마다 사건이 생성되고 감지 범주가 정확하다.

### FR-010 장애 진단 (Diagnosis)

- **설명:** 사건을 장애 코드로 분류하고 권장 전략을 낸다.
- **입력:** 사건 정보, 증거, 시도 이력
- **기대 동작:** F1~F5, REPEATED, UNKNOWN 중 하나와 판단 근거를 낸다.
- **예외 상황:** 규칙에 맞지 않으면 UNKNOWN으로 판정한다.
- **인수조건:** F1~F5 실험의 장애 코드가 주입한 장애와 일치한다. 분류 불가 사례는 UNKNOWN 판정 후 에스컬레이션된다.

### FR-011 복구 실행 (Recovery)

- **설명:** 11장의 정책대로 허용된 복구를 실행한다.
- **입력:** 장애 코드, 승인된 전략
- **기대 동작:** 수행 결과와 recovery_started_at을 기록한다.
- **예외 상황:** 허용목록에 없는 행동은 요청이 와도 실행하지 않는다.
- **인수조건:** 실험 로그에 12.3의 금지 행동 실행이 0건이다. 모든 복구 행동에 시도 횟수가 기록된다.

### FR-012 복구 독립 검증 (Verification)

- **설명:** 복구 후 정상화를 검증한다.
- **입력:** 사건 정보, 복구 결과
- **기대 동작:** 다음을 확인하고 recovered_at을 기록한다.
  - 헬스체크
  - 기준 질문 재처리
  - 근거·권한 확인
  - 단계 중복 확인
- **예외 상황:** 검증할 수 없으면 실패로 판정한다.
- **인수조건:** Verification이 통과시키지 않은 사건 중 RECOVERED·DEGRADED로 끝난 것이 0건이다.

### FR-013 복구 워크플로 제어 (Orchestrator)

- **설명:** 사건 상태와 11장의 공통 정책(시도, 회로, 시간, 비용 상한)을 적용한다.
- **입력:** 각 장애 대응 역할의 출력
- **기대 동작:** 상태 전이를 기록하고, 상한에 도달하면 다음 전략이나 에스컬레이션으로 넘긴다.
- **예외 상황:** 2분을 넘기면 FAILED로 처리한다.
- **인수조건:**
  - 반복 장애 실험에서 연속 3회 실패 후 회로가 열린다.
  - 회로가 열린 동안 자동 복구가 0건이다.
  - 근거 없는 답변이 0건이다.
  - 30초 냉각 후 시험 요청으로 재개 여부가 판정된다.

### FR-014 알림과 에스컬레이션 (Notification)

- **설명:** 사건 결과와 파이프라인 결과를 알림 채널로 보내고 담당자를 할당한다.
- **입력:** 사건 상태, 파이프라인 결과
- **기대 동작:** 메시지에 다음을 포함한다.
  - 오류 유형
  - 요청·사건 ID
  - 장애 단계
  - 담당자
  - 결과(성공·실패·지연·에스컬레이션)
- **예외 상황:** 발송에 실패하면 로컬 기록을 남기고 최대 3회 재발송한다.
- **인수조건:** 반복 장애 실험과 의도적 파이프라인 실패에서 알림과 담당자 할당 기록이 남는다.

### FR-015 장애 주입 (테스트 환경 전용)

- **설명:** F1~F5와 반복 장애를 켜고 끌 수 있게 한다.
- **입력:** 장애 유형, 지속시간
- **기대 동작:** 장애를 활성화하고 injected_at을 기록한다.
- **예외 상황:** 운영 설정에서는 장애 주입을 켤 수 없다.
- **인수조건:** 같은 장애를 3회 반복 주입했을 때 3회 모두 같은 방식으로 재현된다.

### FR-016 검증된 캐시

- **설명:** Critic을 통과한 결과를 권한 등급·문서 버전 정보와 함께 저장하고, 검색 장애 때 재사용한다.
- **입력:** 검증된 결과, 권한 등급, 문서 버전
- **기대 동작:** 폴백할 때 권한 등급과 버전을 다시 확인하고, 응답에 DEGRADED를 표시한다.
- **예외 상황:** 재확인에 실패하면 캐시를 쓰지 않고 응답을 보류한다.
- **인수조건:** F5 실험에서 DEGRADED 응답의 권한·버전이 요청 조건과 일치하고, 권한 밖 노출이 0건이다.

### FR-017 멀티 컨테이너 배포 구성 (평가 P3-2)

- **설명:** 서비스 구성요소를 로컬 쿠버네티스 클러스터에 배포할 매니페스트를 갖춘다.
- **입력:** 구성요소 목록 (API, Worker, 검색 서비스, 저장소, 장애 대응 구성요소)
- **기대 동작:** 다음을 충족한다.
  - 구성요소별 Pod/Service 분리
  - 서비스 이름으로 서로를 찾는 서비스 디스커버리
  - 여러 API 인스턴스에 요청을 나누는 로드밸런싱
  - LLM API 키와 DB 비밀번호를 시크릿으로 관리
  - 헬스체크
  - 저장소 데이터 영속성
- **예외 상황:** 시크릿이 없으면 서비스를 시작하지 않는다. 키를 하드코딩하지 않는다.
- **인수조건:**
  - 매니페스트로 배포한 뒤 모든 구성요소의 헬스체크가 정상이다.
  - API 인스턴스 하나를 중단해도 요청이 처리된다.
  - 저장소와 이미지에 평문 키가 0건이다.

### FR-018 CI/CD 파이프라인 (평가 P3-3)

- **설명:** 커밋 → 빌드 → 테스트(단위·통합) → 배포 → 스모크 테스트 → 알림 단계를 자동 실행한다.
- **입력:** 커밋·PR
- **기대 동작:** 아래 표대로 단계별 입출력을 처리한다. 실패하면 이후 단계를 차단하고 알림을 보낸다.
- **예외 상황:** 단계가 기준 시간을 넘기면 지연 알림을 보낸다. 기준 시간은 [미결정] (U-12).
- **인수조건:**
  - 의도적으로 테스트를 실패시키면 배포 단계가 실행되지 않고 실패 알림이 간다.
  - 수정 후 재실행하면 임시 클러스터 배포와 스모크 테스트가 통과한다.

| 단계 | 입력 | 출력 | 실패 시 처리 |
|---|---|---|---|
| 1. 정적 검사·단위 테스트 | 소스 | 테스트 결과, 커버리지 | 차단, 실패 알림 |
| 2. 이미지 빌드 | 소스 | 버전이 붙은 컨테이너 이미지 | 차단, 실패 알림 |
| 3. 통합 테스트 | 이미지, 테스트 질문 세트, 고정 LLM 응답 | 에이전트 협업·Handoff 테스트 결과 | 차단, 실패 알림 |
| 4. 권한·근거 회귀 테스트 | 테스트 질문 세트 | 권한·근거·핵심 정보 검증 결과 | 차단, 실패 알림 |
| 5. 품질 게이트 | 1~4 결과 | 통과/차단 판정 | 차단, 실패 알림 |
| 6. 임시 클러스터 배포 | 이미지, 매니페스트 | 배포된 서비스 | 차단, 실패 알림 |
| 7. 스모크 테스트 | 배포된 서비스 | 헬스체크·기준 질문 결과 | 실패 알림, 배포 버전 기록 |
| 8. 결과 알림 | 전체 결과 | 성공·실패·지연 알림, 담당자 할당 | 로컬 기록, 재발송 |

### FR-019 지표·사건 기록과 결과 보고

- **설명:** 사건별 시각, 결과, 지표를 기록하고 실험 결과를 집계한다.
- **입력:** 사건 기록, 테스트 결과
- **기대 동작:** 다음을 산출한다.
  - 서비스 품질 지표: 완료율, 날짜·금액·조건 보존율, 권한 위반 건수
  - 장애 유형별 지표: MTTD, MTTR, 수동 개입 없는 복구 비율, 평균 복구 시도 횟수, 에스컬레이션 비율
- **예외 상황:** 시각 필드가 빠진 사건은 집계에서 빼고 따로 표시한다.
- **인수조건:** 데모 시나리오 전체의 집계표가 생성되고, 각 값의 근거 사건 ID를 추적할 수 있다.

## 14. 비기능 요구사항

### NFR-001 안전성

어떤 복구 경로에서도 권한 필터를 건너뛰거나 완화하지 않는다. 검증되지 않은 문서·캐시와 근거 없는 답변은 내보내지 않는다.

- **검증:** 모든 실험에서 권한 밖 노출 0건

### NFR-002 보안

LLM API 키, DB 비밀번호 등 인증정보는 시크릿으로 관리한다. 저장소, 이미지, 로그, 알림에 포함하지 않는다. GitHub 저장소는 공개 또는 조직 공유로 설정한다 (평가 P3-0).

- **검증:** 저장소·로그 검사에서 평문 키 0건

### NFR-003 신뢰성

F1~F5에서 수동 개입 없는 복구 비율이 80% 이상이어야 한다. 복구 후 단계 중복 실행은 0건이어야 한다.

### NFR-004 관측 가능성

15장의 필수 로그 필드를 모든 사건에 기록한다. 요청 ID로 업무 처리와 장애 대응 기록을 연결할 수 있어야 한다.

### NFR-005 성능

- LLM 호출 타임아웃은 10초다.
- 정상 응답시간 기준과 MTTR 목표는 [미결정]이다 (U-06). 정상 기준선을 측정한 뒤 확정한다.

### NFR-006 재현성

- 장애 주입은 같은 조건에서 반복해 재현할 수 있어야 한다.
- 파이프라인 테스트는 실제 LLM 대신 고정 응답을 써서 결과가 흔들리지 않게 한다.
- 실제 LLM은 통합 실험과 데모에서 사용한다.

### NFR-007 설명 가능성

모든 답변에 근거 문서 ID와 인용 위치를 붙인다. 모든 진단·복구 결정에 판단 근거를 기록한다.

### NFR-008 비용 통제

요청별·일별 LLM 호출 및 비용 상한을 두고, 상한에 도달하면 자동 재시도를 멈춘다. 수정 루프는 2회로 제한한다. 상한 수치는 [미결정]이다 (U-02).

### NFR-009 테스트 품질

- 핵심 로직 테스트 커버리지는 80% 이상이어야 한다.
- 다음 중 하나라도 해당하면 배포를 차단한다.
  - 필수 테스트 실패
  - 권한 노출 1건 이상
  - Handoff 필수 필드 누락 1건 이상

### NFR-010 확장성

자료 적재는 공통 메타데이터 구조를 따른다. 새 자료 유형을 추가하거나 업로드·자동 파싱 경로를 붙여도 검색·권한·검증 로직을 바꾸지 않아야 한다.

- **검증:** MVP에서는 4개 자료 유형을 같은 처리 경로로 질의할 수 있음을 테스트 질문으로 확인

## 15. 데이터와 로그 요구사항

### 15.1 데이터

- **아카이브:** 매뉴얼, 정책, 경영자료, 업무자료의 가상 문서 10~12개 (유형별 2~3개). 구체적 문서 목록은 [미결정]이다 (U-05).
- **문서 메타데이터:** FR-001에 정의한 공통 구조를 따른다.
- **권한:** 3등급. 경영자료는 상위 등급만 접근할 수 있다. 등급 명칭과 매핑은 [미결정]이다 (U-07).
- **테스트 질문 세트:** 20개. 다음 유형을 포함한다.
  - 절차형, 정보형, 여러 문서에 걸친 질문
  - 권한 등급별 차이
  - 근거 부족
  - 권한 밖 요청
  - 날짜·금액·조건 보존 확인
- **테스트 데이터 관리:** 테스트 질문 세트, 기대 결과, 고정 LLM 응답은 저장소에서 버전 관리한다. 실제 데이터와 개인정보는 넣지 않는다.

### 15.2 필수 로그 필드

| 필드 | 설명 |
|---|---|
| incident_id, trace_id(요청 ID) | 사건·요청 추적 |
| injected_at, detected_at, recovery_started_at, recovered_at | 시간 측정 |
| 탐지 근거, 진단 결과와 근거 | 판단 추적 |
| 복구전략, 도구 호출 인자, 실행 결과, 시도 횟수, 수정 루프 횟수 | 복구 추적 |
| 사용 모델(기본/대체), LLM 호출 수·토큰·비용 | 비용 추적 |
| 승인자와 승인 결과 | 사람 개입 추적 |
| 검증 결과 | 독립 검증 근거 |
| 알림 발송 결과, 담당자 | 에스컬레이션 추적 |
| 최종 상태 | SUCCESS / RECOVERED / DEGRADED / FAILED / BLOCKED / ESCALATED |

### 15.3 민감정보 제외

- 인증정보는 기록하지 않는다.
- 권한 밖 문서(특히 경영자료)는 원문 대신 문서 ID만 기록한다.

로그 저장 위치, 보존 기간, 시간 형식과 타임존은 [미결정]이다 (U-10).

## 17. 3일 MVP 포함·제외 범위

### 포함

- 자동 알림과 에스컬레이션
- 평가 산출물 P3-0 ~ P3-3

6장 비목표와 같다.
