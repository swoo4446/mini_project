## 2. 프로젝트 개요

OrderOps AI는 단체 채팅방의 주문 대화와 주문할 카페 브랜드를 입력받아, 주문을 추출·정규화·검증하고 개인별 확인과 담당자 확정을 거쳐 매장 주문서와 개인별 정산 내역을 생성하는 서비스다.

이 프로젝트의 핵심은 **이 서비스를 보호하는 장애 자가 복구 워크플로**다. 주문 처리 중 의존 서비스가 실패·지연되거나 처리 프로세스가 중단되면, 장애 대응 역할들이 장애를 탐지·진단하고 허용된 범위에서 복구한 뒤 정상화 여부를 독립적으로 검증한다. 복구할 수 없으면 상태를 보존하고 사람에게 넘긴다.

**한 문장 정의**

> 사용자가 단체 채팅 주문 대화와 주문 브랜드를 입력해 분석을 요청하면, 서비스는 주문 해석 의존 서비스와 선택한 브랜드의 메뉴 데이터를 이용해 주문을 추출·정규화·검증하고, 개인별 확인과 담당자 확정을 거쳐 매장 주문서와 개인별 정산 내역을 반환한다.

**구성 계층**

| 계층 | 역할 |
|---|---|
| 업무 층 (보호 대상 서비스) | 주문 이벤트 추출 → 브랜드 메뉴 정규화 → 주문 검증 → 개인 확인·확정 → 집계·정산 |
| 장애 대응 층 (Auto Healing) | Monitor → Diagnosis → Recovery → Verification, Orchestrator가 흐름·한도 관리, Notification이 사람에게 전달 |

## 3. 문제 정의

### 3.1 사용자 문제

단체 주문 담당자는 채팅방의 주문 대화를 보며 수기로 취합한다. 약칭·옵션 해석, 중간에 바뀐 주문과 취소 반영, 누락·중복 확인, 메뉴별 수량 집계, 개인별 금액 계산을 모두 사람이 처리하므로 시간이 오래 걸리고 오류가 생긴다. 참여자는 자신의 주문이 맞게 들어갔는지 확인할 방법이 없다.

### 3.2 운영 문제

주문 처리 중 장애가 나면 운영자는 사용자 문의나 화면을 보고서야 장애를 알게 된다. 로그를 열어 원인을 직접 판단하고, 프로세스를 재시작하고, 작업을 처음부터 다시 실행한다. 재실행 과정에서 주문이 중복·유실되거나 개인 확인 상태가 어긋날 수 있지만 이를 체계적으로 확인할 방법이 없고, 대응 기록도 남지 않는다.

### 3.3 서비스 중단 영향

| 구분 | 영향 |
|---|---|
| 사용자 | 담당자는 분석 결과·주문서·정산표를 받지 못하고 수기로 다시 정리. 참여자는 개인 확인을 진행하지 못하거나 재확인을 요구받음 |
| 운영 | 수동 탐지·진단·재실행, 중복·유실·확인 상태의 수동 점검 |
| 데이터·비용·보안 | 실제 결제·개인정보 없음(가상 데이터). 재처리 시 주문 중복·유실로 정산 오류 가능. 개인 확인 링크 노출 시 해당 주문 내역 노출 가능 |
| 심각도 | 중간 — 일부 요청이 실패하고 운영자 대응이 필요하나 금전 피해로 직결되지 않음 |

### 3.4 서비스 경계

- 포함: 채팅·브랜드 입력부터 주문서·정산 생성까지의 주문 서비스, 이를 보호하는 장애 대응 워크플로, 장애 주입 수단, CI/CD 품질 게이트
- 제외: 실제 매장 주문 전송, 결제·송금, 메신저 연동, 카페 외 카테고리 주문

## 5. 목표와 성공 기준

### 5.1 목표

| ID | 목표 |
|---|---|
| G-1 | 채팅·브랜드 입력부터 주문서·개인별 정산 생성까지의 정상 흐름을 제공한다. |
| G-2 | 지정된 장애 시나리오에서 자동 복구 성공 여부를 판정하고, 장애 주입·탐지·정상화 시점을 기록해 MTTD·MTTR을 산출한다. |
| G-3 | 복구 전후로 주문 데이터 무결성(중복·유실 없음, 개인 확인 상태 보존, 정산 일치)을 유지한다. |
| G-4 | 자동 복구가 실패하거나 원인이 불명확하면 상태를 보존하고 사람에게 에스컬레이션한다. |
| G-5 | 필수 테스트가 실패한 변경은 배포되지 않는다. |

### 5.2 성공 기준

| ID | 성공 기준 | 측정 방법 |
|---|---|---|
| SC-1 | 정상 기준선: 기준 채팅·브랜드 5건 처리 시 주문 수량·정산이 정답 데이터와 100% 일치 | 정답 데이터 비교 |
| SC-2 | MTTD 15초 이하 | `detected_at - injected_at` |
| SC-3 | MTTR: 5xx·타임아웃 60초 이하, 프로세스 중단 90초 이하 | `recovered_at - injected_at` |
| SC-4 | 복구 가능 장애 3종(5xx, 타임아웃, 프로세스 중단)을 각 5회 반복 시 자동 복구 성공률 80% 이상 | 성공 건수 ÷ 전체 주입 건수 |
| SC-5 | 모든 장애 실험에서 주문 중복·유실 0건, 개인 확인 상태 보존, 개인별 합계 = 전체 금액 | Verification 결과 |
| SC-6 | 반복 장애 시 회로 차단 발생, 자동 복구 실패 시 FAILED 상태 보존과 에스컬레이션 기록 100% | 사건 로그 |
| SC-7 | 필수 테스트를 의도적으로 실패시킨 변경은 배포 100% 차단 | CI 실행 기록 |
| SC-8 | 등록되지 않은 메뉴·옵션의 자동 확정 0건 | 테스트 결과 |

> 수치는 근거를 붙인 초안을 우선 확정한 값이며 실험 결과에 따라 수정할 수 있다.

## 6. 비목표

- 실제 매장 주문 전송, 결제, 송금, 환불
- 운영 개인정보 사용 (가명·가상 브랜드·메뉴만 사용)
- 카페 외 카테고리(치킨·피자·햄버거)의 실제 주문 기능, 브랜드·매장 메뉴 자동 연동
- 메신저 실시간 연동, 개인 확인 링크 자동 발송
- 회원가입·본인 인증, 메뉴 추천, 실시간 공동 편집, 할인·쿠폰·세트, 고급 관리자 대시보드
- 운영 클라우드 인프라 변경, 비용 한도 없는 리소스 확장
- LLM이 생성한 임의 명령의 자동 실행 등 완전 자율 복구

## 7. 정상 서비스 시나리오

### 7.1 정상 흐름

```text
주문 담당자
  ↓ ① 채팅 붙여넣기 + 카페 브랜드 선택 (한 화면, 순서 무관)
주문 서비스
  ↓ ② 주문 이벤트 추출 (주문 해석 서비스 호출)
  ↓ ③ 브랜드 메뉴·옵션·가격 정규화 (브랜드 메뉴 저장소)
  ↓ ④ 주문 검증 → 확인 필요 항목 표시
주문 담당자
  ↓ ⑤ 검토·개별 수정 (해당 주문만 재검증)
  ↓ ⑥ 개인 확인 링크 복사·전달
주문 참여자
  ↓ ⑦ 확인 완료 또는 수정 요청
주문 담당자
  ↓ ⑧ 확정 조건 충족 시 최종 확정 (버전 고정)
주문 서비스
  ↓ ⑨ 집계·정산
정상 결과: 매장 주문서 + 개인별 정산 내역 + 주문 처리 결과
```

### 7.2 대표 입력과 결과

입력(브랜드: 가상 카페 브랜드 A):

```text
[김민수] 아이스 아메리카노 톨 2잔, 하나는 샷 추가요.
[이지연] 바닐라라떼 큰 거 얼음 적게요.
[박서연] 아아 톨 한 잔이요.
[김민수] 아까 샷 추가한 한 잔 취소할게요.
[이지연] 사이즈는 벤티로 할게요.
```

기대 결과: 김민수 아이스 아메리카노 톨 1, 이지연 아이스 바닐라라떼 벤티 얼음 적게 1, 박서연 아이스 아메리카노 톨 1, 합계 3. "큰 거"는 확인 요청 후 "벤티로" 메시지로 확정된다.

### 7.3 업무 상태

| 상태 | 의미 |
|---|---|
| PENDING | 분석 대기 |
| RUNNING | 분석 실행 중 |
| NEEDS_REVIEW | 담당자 확인 필요 항목 존재 |
| AWAITING_CONFIRMATION | 검증 완료, 개인 확인 진행 중 |
| CONFIRMED | 담당자 최종 확정 (버전 고정) |
| COMPLETED | 주문서·정산 생성 완료 |
| FAILED | 자동 복구 실패, 상태 보존 |

개인 확인 상태: 확인 대기 / 확인 완료 / 수정 요청

> 상태 이름은 개념 정의이며 실제 스키마는 상세 설계 단계에서 확정한다.

## 8. 장애 시나리오

### 8.1 대상 장애

| ID | 장애 | 발생 위치 | 탐지 신호 | 사용자·운영 영향 | 안전한 재현 방법 |
|---|---|---|---|---|---|
| F-1 | HTTP 5xx (일시적) | 주문 해석 서비스 | 5xx 응답, 오류율 상승 | 분석 실패 | 모의 서비스의 오류 모드 전환 |
| F-2 | 응답 지연·타임아웃 | 주문 해석 서비스 | 호출 제한시간(5초) 초과 | 분석 지연·실패 | 모의 서비스의 지연 모드 전환 |
| F-3 | 프로세스 중단 | 주문 처리 프로세스 | 헬스체크 연속 실패, 작업 정체 | 진행 중 작업 중단, 중복·유실 위험 | 실습 전용 환경에서 처리 프로세스 종료 |
| F-4 | 동일 장애 반복 | 주문 해석 서비스 | 같은 의존 서비스의 연속 사건 | 무한 재시도 위험 | 오류 모드를 계속 유지 |

### 8.2 선택 장애 (여유 시 추가)

| ID | 장애 | 재현 방법 |
|---|---|---|
| F-5 | 잘못된 출력(스키마 위반) | 모의 서비스가 필수 필드가 빠진 응답 반환 |
| F-6 | 메뉴 저장소 조회 실패 | 실습 환경의 저장소 연결 차단 |

### 8.3 장애가 아닌 업무 규칙

다음은 장애가 아니라 업무 규칙·데이터 무결성 요구사항으로 다룬다(13장).

- 개인 확인 후 주문 내용 변경 → 해당 확인 무효화·재확인
- 동일 채팅 재입력 → 기존 결과 반환, 중복 반영 방지
- 정산 불일치 → 확정 차단

## 9. 멀티 에이전트 구성

> 역할은 개념 수준으로 정의한다. 규칙·함수·상태기계로 충분한 역할은 별도 LLM 에이전트로 만들지 않는다. 역할별 구현 형태는 [미결정] (U-05).

### 9.1 업무 층 처리 단계 (보호 대상)

| 단계 | 책임 | 처리 원칙 |
|---|---|---|
| Intake | 메시지에서 주문 추가·수정·취소·확정·무관 이벤트 추출 | 주문 해석 서비스 사용. 모호하면 임의 확정하지 않음 |
| Menu | 선택한 브랜드의 메뉴·사양·옵션과 매칭 | 존재 여부·가격은 등록된 메뉴 데이터로만 판정 |
| Validation | 누락·중복·옵션·수량·수정 관계 검증 | 규칙 기반 |
| Settlement | 확정 주문 집계, 개인별 금액·주문서 생성 | 계산 규칙으로 처리 (AI 미사용) |

업무 층의 Validation(주문 검증)과 장애 대응 층의 Verification(복구 검증)은 다른 역할이다.

### 9.2 장애 대응 층

#### Monitor

- 책임: 장애 신호 관찰과 사건 생성
- 입력: 헬스체크 응답, 애플리케이션 로그, 오류율, 응답시간, 프로세스 상태, 작업 상태·체크포인트 갱신 시각
- 출력: 사건(사건 ID, 대상, 관찰 신호, 탐지 근거, 탐지 시각)
- 사용할 수 있는 정보: 관찰 데이터 조회
- 허용 행동: 조회, 사건 생성
- 금지 행동: 설정 변경, 복구 실행
- 실패 시 행동: 관찰 실패 자체를 사건으로 기록하고 Orchestrator에 전달

#### Diagnosis

- 책임: 증거를 바탕으로 장애 유형 분류와 복구안 제안
- 입력: 사건, 탐지 근거, 최근 로그·상태, 시도 이력
- 출력: 장애 코드(DEP_HTTP_5XX, DEP_TIMEOUT, WORKER_DOWN, REPEATED_FAILURE, UNKNOWN), 판단 근거, 추천 복구 전략
- 사용할 수 있는 정보: 사건·로그·상태·시도 이력 조회
- 허용 행동: 증거 조회, 복구안 제안
- 금지 행동: 복구 직접 실행
- 실패 시 행동: UNKNOWN으로 분류, 자동 변경 없이 에스컬레이션

#### Recovery

- 책임: 승인된 복구 전략 실행
- 입력: Orchestrator가 전달한 복구 전략과 사건
- 출력: 복구 수행 결과(전략, 시도 번호, 시작·종료 시각, 결과)
- 사용할 수 있는 정보: 대상 사건, 허용목록, 체크포인트
- 허용 행동: 제한된 재시도(지수 백오프), 사전 승인된 대체 주문 해석 서비스 전환, 허용목록 내 처리 프로세스 재시작, 체크포인트부터 재개
- 금지 행동: 임의 명령 실행, 허용목록 밖 재시작, 주문·확인·정산 데이터 삭제·임의 수정, 확정 버전 덮어쓰기, 한도 우회
- 실패 시 행동: 결과를 실패로 보고. 복구 완료를 스스로 선언하지 않음

#### Verification

- 책임: 복구 결과의 독립 검증
- 입력: 사건, 복구 수행 결과, 기준선 측정값, 정답 데이터
- 출력: 정상화 판정(성공·실패)과 근거, 판정 시각
- 사용할 수 있는 정보: 헬스체크, 기능·회귀 테스트 결과, 주문·확인·정산 데이터 조회
- 허용 행동: 헬스체크, 기능 검증, 데이터 무결성 확인
- 금지 행동: 복구 실행, 검증 없는 완료 선언
- 실패 시 행동: 복구 실패로 판정하고 Orchestrator에 전달

#### Orchestrator

- 책임: 역할 호출 순서, 사건 상태, 시도 횟수, 회로 상태, 전체 타임아웃 관리
- 입력: 사건, 각 역할의 출력
- 출력: 다음 행동 결정(진단·복구·검증·에스컬레이션·종료)
- 사용할 수 있는 정보: 사건 기록, 시도 이력, 회로 상태, 정책 수치
- 허용 행동: 역할 호출, 에스컬레이션 결정
- 금지 행동: 재시도 상한·회로 차단·권한 제한 우회, 서비스·데이터 직접 조작
- 실패 시 행동: 사건을 FAILED로 보존하고 에스컬레이션

**필요성:** 순서·한도·동시 재실행 방지를 한곳에서 관리해야 무한 루프와 중복 복구를 막을 수 있다.

#### Notification

- 책임: 사람에게 결과 전달과 승인 요청
- 입력: 최종 상태, 증거, 추천 행동
- 출력: 운영자 화면의 승인 요청 표시, 외부 메신저 알림
- 사용할 수 있는 정보: 사건 요약
- 허용 행동: 보고, 승인 요청, 재알림
- 금지 행동: 복구 정책 변경, 복구 실행
- 실패 시 행동: 알림 실패를 로그에 기록하고 화면 표시는 유지

## 10. 에이전트 협업 흐름

```text
[장애 발생]
  ↓
[Monitor — 신호 관찰, 사건 생성]
  ↓
[Orchestrator — 시도 횟수·회로 상태·냉각시간 확인]
  ↓
[Diagnosis — 장애 유형 분류]
  ├─ UNKNOWN → [상태 보존 → Notification: 운영자 승인 요청]
  ↓
[Recovery — 허용된 복구 실행]
  ↓
[Verification — 독립 검증]
  ├─ 성공 → [사건 종료, 지표·로그 기록]
  └─ 실패 → [Orchestrator]
              ├─ 상한 이내 → 다음 전략 (재시도 → 대체 전환 / 재시작 → 재개)
              └─ 상한·회로 차단·5분 초과 → [FAILED 보존 → Notification: 에스컬레이션]
```

- Recovery의 성공 보고만으로 사건을 종료하지 않는다. Verification 판정만 종료 근거가 된다.
- 사용자 화면에는 "주문 내역은 저장되어 있어요. 중단된 작업을 다시 진행합니다."처럼 행동 중심 안내만 표시하고, 기술 정보는 운영자 화면과 로그에 남긴다.

## 11. 장애별 복구정책

| 장애 | 탐지 신호 | 진단 근거 | 1차 복구 | 2차 복구 | 최대 시도 | 사람 승인 | 롤백 | 성공 검증 |
|---|---|---|---|---|---:|---|---|---|
| F-1 HTTP 5xx | 5xx 응답, 헬스체크 연속 2회 실패 | 응답 코드 | 지수 백오프 재시도 (1→2→4초) | 대체 주문 해석 서비스 전환 | 1차 3회 + 대체 2회 | 불필요 (상한 초과 시 에스컬레이션) | 1차 정상화(헬스체크 연속 3회) 시 기존 경로 복원 | 헬스체크 연속 3회 정상, 검증 요청 5건 실패 0건, 기능 테스트 통과 |
| F-2 타임아웃 | 호출 5초 초과 | 제한시간 초과 | 지수 백오프 재시도 (1→2→4초) | 대체 주문 해석 서비스 전환 | 1차 3회 + 대체 2회 | 불필요 (상한 초과 시 에스컬레이션) | 1차 정상화 시 기존 경로 복원 | 응답시간 기준선 2배 이내, 기능 테스트 통과 |
| F-3 프로세스 중단 | 헬스체크 연속 2회 실패, 체크포인트 60초 이상 미갱신 | 프로세스 상태 | 허용목록 내 재시작 (준비 대기 최대 30초) | 마지막 성공 체크포인트부터 재개 (작업 ID 잠금) | 10분 내 재시작 2회 | 불필요 (허용목록·테스트 환경 한정) | 재개 결과 불일치 시 미반영, 기존 확정 버전 유지 후 에스컬레이션 | 헬스체크 정상, 중복·유실 0건, 개인 확인 상태 보존 |
| F-4 반복 장애 | 같은 의존 서비스 연속 사건 3건 | 연속 발생 횟수 | 회로 차단, 자동 복구 중단 | 60초 후 시험 요청 1회 | — | 시험 요청 실패 시 운영자 승인 필요 | 해당 없음 (변경 없음) | 회로 상태·에스컬레이션 기록 |

**공통 정책**

| 항목 | 값 | 근거 |
|---|---|---|
| 헬스체크 주기 / 장애 판정 | 5초 / 연속 2회 실패 | 탐지 지연을 짧게 하면서 순간 오류로 인한 오탐 감소 |
| 의존 서비스 호출 제한시간 | 5초 | 모의 응답(1초 미만)의 5배 이상. 실제 LLM 연결 시 재조정 |
| 백오프 | 지수 1→2→4초, 무작위 지연 없음 | 호출 주체가 하나라 요청 집중 위험이 없고 측정 재현성 우선 |
| 냉각시간 | 같은 장애·같은 전략 30초 내 재실행 금지 | 같은 전략의 연속 반복 방지 |
| 회로 차단 / 재개 | 연속 3건 / 60초 후 시험 요청 1회, 실패 시 사람 승인 | 자동 재개는 1회만, 이후는 사람 판단 |
| 사건 전체 타임아웃 | 5분 | 모든 복구 경로와 검증을 포함해도 충분한 상한 |

> 정책 수치는 우선 확정 값이며 실험 결과에 따라 수정한다.

## 12. 자율성과 Human-in-the-loop

### 12.1 자동 실행 가능

| 행동 | 조건 |
|---|---|
| 의존 서비스 호출 재시도 (지수 백오프) | 시도 상한 이내, 회로 닫힘 |
| 사전 승인된 대체 주문 해석 서비스 전환 | 1차 상한 초과, 대체 서비스 헬스체크 정상 |
| 허용목록 내 주문 처리 프로세스 재시작 | 실습 전용 환경, 10분 내 2회 이내 |
| 마지막 성공 체크포인트부터 재개 | 체크포인트 존재, 같은 작업이 실행 중이 아님 |
| 헬스체크·기능 검증 재실행 | 제한 없음 (조회 행동) |
| 회로 차단 후 시험 요청 1회 | 60초 경과 |

### 12.2 사람 승인 후 실행

| 행동 | 승인자 | 승인 방식 | 승인 타임아웃 | 미승인 시 |
|---|---|---|---:|---|
| 설정 변경 | 운영자 | 운영자 화면 | 10분 | 변경 없음, FAILED 보존, 재알림 |
| 시험 요청 실패 후 회로 재개 | 운영자 | 운영자 화면 | 10분 | 회로 열림 유지, 재알림 |
| 원인 불명(UNKNOWN) 장애 조치 | 운영자 | 운영자 화면 | 10분 | 자동 변경 없이 대기, 재알림 |

- 재알림: 10분 간격, 최대 3회. 알림 수단은 외부 메신저 알림.
- 업무 승인(복구 승인과 별개): 개인 주문 확인은 주문 참여자, 최종 확정은 주문 담당자가 수행한다.

### 12.3 자동 실행 금지

- LLM 등이 생성한 임의 쉘 명령 실행
- 허용목록에 없는 서비스 재시작
- 주문·확인·정산 데이터 삭제 또는 임의 수정, 확정 주문 버전 덮어쓰기
- 운영 데이터베이스 변경, 인증정보 변경
- 비용 한도 없는 리소스 생성·확장
- 실제 결제·송금

## 13. 기능 요구사항

> 모든 기능 요구사항은 P0(3일 MVP 필수)이다.

### 13.1 주문 서비스 (업무 층)

### FR-001 채팅·브랜드 통합 입력

- 설명: 채팅 입력과 카페 브랜드 선택을 한 화면에서 순서 무관하게 제공한다.
- 입력: 채팅 텍스트, 브랜드 선택(가상 카페 브랜드 2개 중 하나)
- 기대 동작: 둘 다 입력되어야 `주문 분석하기`가 활성화된다. 예시 대화 불러오기와 지원 형식 안내를 제공한다.
- 예외 상황: 브랜드 미선택, 빈 입력
- 인수조건: 채팅 또는 브랜드 중 하나라도 없으면 분석이 시작되지 않는다.

### FR-002 채팅 파싱과 원본 보존

- 설명: `[이름] 메시지` 형식을 발신자·메시지·순서로 분리하고 원본을 보존한다.
- 입력: 채팅 텍스트
- 기대 동작: 메시지마다 식별자와 입력 순서를 부여한다. 분석 실패·브랜드 변경 시에도 원본 채팅을 유지한다.
- 예외 상황: 지원하지 않는 형식의 줄
- 인수조건: 지원하지 않는 형식은 해당 줄과 수정 방법을 안내한다. 분석 실패 후 화면에 원본이 그대로 남아 있다.

### FR-003 주문 이벤트 추출

- 설명: 메시지를 ADD·UPDATE·CANCEL·CONFIRM·IGNORE 이벤트로 해석한다.
- 입력: 파싱된 메시지, 입력 순서
- 기대 동작: 수정·취소·확정은 이전 주문과 연결하고, 각 이벤트에 원문 메시지 근거를 남긴다.
- 예외 상황: 수정·취소 대상이 모호함
- 인수조건: 모호한 수정·취소는 임의 처리하지 않고 확인 필요로 표시된다. 7.2 대표 입력에서 기대 결과가 나온다.

### FR-004 브랜드 메뉴 정규화

- 설명: 메뉴명·약칭·사이즈·온도·옵션을 선택한 브랜드의 메뉴 데이터와 매칭한다.
- 입력: 주문 이벤트, 브랜드 메뉴 데이터(브랜드당 메뉴 5~8개)
- 기대 동작: 표준 메뉴·사양·옵션과 가격, 메뉴 데이터 버전을 연결한다.
- 예외 상황: 미등록 메뉴·옵션, 모호한 사양("큰 거")
- 인수조건: 미등록 메뉴·옵션은 자동 확정되지 않는다(SC-8). 가격이 없는 항목은 정산 대상이 되지 않는다.

### FR-005 주문 검증

- 설명: 누락·중복·옵션 유효성·수량(양의 정수)·수정 관계를 검증한다.
- 입력: 정규화된 주문
- 기대 동작: 항목별 검증 상태(통과·확인 필요·실패)와 사유를 생성한다.
- 예외 상황: 필수 정보 누락
- 인수조건: 확인 필요 항목이 있으면 세션 상태가 NEEDS_REVIEW가 된다.

### FR-006 결과 검토와 개별 수정

- 설명: 담당자가 분석 결과를 검토하고 항목별로 수정한다.
- 입력: 분석 결과, 담당자 수정
- 기대 동작: 확인 필요 항목을 상단에 표시하고 요약(주문자 수, 주문 수량, 확인 필요 건수, 정상 건수)을 보여준다. 수정 시 해당 주문만 재검증한다.
- 예외 상황: 수정 결과가 다시 검증 실패
- 인수조건: 수정 후 전체 재분석 없이 해당 항목의 검증 상태만 갱신된다. 수정·취소의 원문을 확인할 수 있다.

### FR-007 개인 확인

- 설명: 주문자별 확인 링크로 참여자가 자신의 주문을 확인하거나 수정을 요청한다.
- 입력: 검증 완료 주문, 참여자 응답(확인 완료 / 수정 요청 + 사유)
- 기대 동작: 주문자별 만료형 무작위 토큰 링크(24시간)를 생성하고, 담당자가 링크와 요청 문구를 복사할 수 있다. 참여자 화면에는 브랜드, 본인 주문, 개인 금액만 표시한다.
- 예외 상황: 만료된 링크, 확인 후 주문 변경
- 인수조건: 링크로 다른 주문자의 내역을 볼 수 없다. 확인 완료 후 해당 주문이 바뀌면 확인 상태가 대기로 돌아간다. 만료된 링크는 접근이 거부된다.

### FR-008 브랜드 변경 정책

- 설명: 진행 단계별로 브랜드 변경을 처리한다.
- 입력: 브랜드 변경 요청, 현재 세션 상태
- 기대 동작: 분석 전에는 자유 변경, 분석 후에는 결과 무효화 안내 후 재분석, 개인 확인 이후에는 확인 상태 취소와 재검증·재확인, 확정 후에는 새 주문 버전으로 진행한다.
- 예외 상황: 확정 후 변경 시도
- 인수조건: 모든 단계에서 원본 채팅이 유지된다. 확정된 버전은 변경되지 않는다.

### FR-009 최종 확정과 버전 고정

- 설명: 확정 조건이 모두 충족되면 담당자가 최종 확정한다.
- 입력: 세션 상태, 개인 확인 현황
- 기대 동작: 확인 현황(전체·완료·대기·수정 요청 인원, 수량, 예상 총액)을 보여준다. 조건은 검증 완료, 미해결 확인 항목 0건, 변경·취소 반영, 전원 확인 완료, 개인별 합계 = 전체 금액이다.
- 예외 상황: 조건 미충족
- 인수조건: 조건 미충족 시 확정 버튼이 비활성화되고 사유와 해당 주문으로 이동 수단이 표시된다. 확정 후 버전이 고정된다.

### FR-010 산출물 생성

- 설명: 확정 버전으로 매장 주문서, 개인별 정산 내역, 주문 처리 결과를 생성한다.
- 입력: 확정 주문 버전
- 기대 동작: 주문서(브랜드, 메뉴·사양·옵션별 수량, 단가, 금액, 총액)와 정산(주문자별 상세, 옵션 추가 금액, 개인 합계, 전체 금액)을 탭으로 분리한다. 처리 결과에는 변경·취소 이력, 확인 현황, 검증·복구 결과, 확정 버전을 표시한다. CSV 다운로드와 인쇄용 화면을 제공한다.
- 예외 상황: 확정되지 않은 세션
- 인수조건: 확정 전에는 산출물이 생성되지 않는다. 개인별 합계의 합이 전체 금액과 같다.

### FR-011 Snapshot 중복 방지

- 설명: 매번 전체 채팅을 입력하는 Snapshot 방식에서 중복 반영을 막는다.
- 입력: 동일 세션의 채팅 재입력
- 기대 동작: 동일 내용이면 기존 분석 결과를 반환한다. 내용이 다르면 새 Snapshot 버전으로 재분석하되, 검증 전에는 기존 확정 결과를 덮어쓰지 않는다.
- 예외 상황: 내용이 같은 별개의 주문 메시지
- 인수조건: 동일 Snapshot 재입력 시 주문 중복 0건. 내용이 같다는 이유만으로 별개 주문이 삭제되지 않는다.

### FR-012 진행 상태와 사용자 안내

- 설명: 분석·검증·확인·완료 상태와 오류를 이해하기 쉬운 문구로 안내한다.
- 입력: 세션·작업 상태
- 기대 동작: "주문 내용을 읽고 있어요" 등 단계 안내, 장애 시 "주문 내역은 저장되어 있어요"처럼 행동 중심 안내를 표시한다.
- 예외 상황: 복구 실패
- 인수조건: 사용자 화면에 기술 오류 메시지·내부 역할 이름이 노출되지 않는다.

### 13.2 장애 대응 워크플로 (장애 대응 층)

### FR-013 작업 상태와 체크포인트 저장

- 설명: 업무 단계마다 완료 상태와 중간 결과를 영속 저장한다.
- 입력: 단계 실행 결과
- 기대 동작: 세션 ID, Snapshot 버전, 브랜드·메뉴 버전, 단계, 체크포인트를 저장한다. 작업 ID 기반으로 동시 재실행을 막는다.
- 예외 상황: 저장 실패
- 인수조건: 프로세스 재시작 후 미완료 작업과 마지막 성공 단계를 조회할 수 있다.

### FR-014 장애 탐지와 사건 생성

- 설명: Monitor가 관찰 데이터로 장애를 판정하고 사건을 생성한다.
- 입력: 헬스체크(5초 주기), 로그, 오류율, 응답시간, 프로세스·작업 상태
- 기대 동작: 연속 2회 실패, 5초 초과, 체크포인트 60초 이상 미갱신 시 사건을 생성한다.
- 예외 상황: 단발성 오류
- 인수조건: 단발성 1회 실패로는 사건이 생성되지 않는다. F-1~F-3 주입 시 MTTD 15초 이하.

### FR-015 장애 진단

- 설명: Diagnosis가 사건을 장애 코드로 분류하고 복구안을 제안한다.
- 입력: 사건, 증거, 시도 이력
- 기대 동작: 규칙에 따라 DEP_HTTP_5XX·DEP_TIMEOUT·WORKER_DOWN·REPEATED_FAILURE·UNKNOWN 중 하나로 분류하고 근거를 남긴다.
- 예외 상황: 규칙 불일치
- 인수조건: F-1~F-4 주입 시 각각 올바른 코드로 분류된다. 분류 불가 시 UNKNOWN과 에스컬레이션이 기록된다.

### FR-016 재시도와 대체 서비스 전환

- 설명: 의존 서비스 장애 시 제한된 재시도 후 사전 승인된 대체 서비스로 전환한다.
- 입력: DEP_HTTP_5XX 또는 DEP_TIMEOUT 사건
- 기대 동작: 1차 최대 3회(1→2→4초) 후 대체 서비스 헬스체크가 정상이면 전환해 최대 2회 시도한다. 1차가 헬스체크 연속 3회 정상이면 기존 경로로 복원한다.
- 예외 상황: 대체 서비스도 실패
- 인수조건: 시도 횟수가 상한을 넘지 않는다. 대체 서비스도 실패하면 에스컬레이션된다.

### FR-017 프로세스 재시작과 체크포인트 재개

- 설명: 처리 프로세스 중단 시 허용목록 기반으로 재시작하고 체크포인트부터 재개한다.
- 입력: WORKER_DOWN 사건, 허용목록, 체크포인트
- 기대 동작: 10분 내 최대 2회 재시작, 준비 대기 최대 30초. 마지막 성공 단계부터 재개한다.
- 예외 상황: 재시작 상한 초과, 재개 결과 불일치
- 인수조건: 재개 후 주문 중복·유실 0건, 개인 확인 상태 보존. 허용목록 밖 대상은 재시작되지 않는다.

### FR-018 무한 루프 방지

- 설명: 회로 차단, 냉각시간, 전체 타임아웃으로 복구 반복을 제한한다.
- 입력: 사건 이력, 회로 상태
- 기대 동작: 같은 의존 서비스 연속 사건 3건이면 회로를 열고 자동 복구를 중단한다. 60초 후 시험 요청 1회, 실패 시 사람 승인 필요. 같은 전략은 30초 안에 재실행하지 않는다. 사건당 5분을 넘기면 FAILED로 보존한다.
- 예외 상황: 회로가 열린 상태의 신규 장애
- 인수조건: F-4 주입 시 회로 차단과 에스컬레이션이 기록되고, 회로가 열린 동안 자동 복구 시도가 0건이다.

### FR-019 독립 복구 검증

- 설명: Verification이 복구 결과를 측정값으로 판정한다.
- 입력: 사건, 복구 결과, 기준선, 정답 데이터
- 기대 동작: 헬스체크 2초 간격 연속 3회 정상, 검증 요청 5건 실패 0건, 응답시간 기준선 2배 이내, 기준 채팅·브랜드 5건의 정답 일치, 중복·유실 0건, 개인 확인 상태 보존을 모두 확인한다.
- 예외 상황: 일부 항목 미달
- 인수조건: Recovery 보고만으로 사건이 종료되지 않는다. 하나라도 미달이면 복구 실패로 판정된다.

### FR-020 에스컬레이션과 승인

- 설명: 자동 복구 실패·원인 불명·회로 재개 시 사람에게 넘긴다.
- 입력: FAILED 또는 승인 필요 사건
- 기대 동작: 운영자 화면에 사건 요약·증거·추천 행동과 승인·거부 버튼을 표시하고 외부 메신저로 알린다. 10분 미응답 시 10분 간격 최대 3회 재알림한다.
- 예외 상황: 알림 전송 실패
- 인수조건: 에스컬레이션 시 상태가 보존되고, 승인 결과(승인자·시각·결정)가 기록된다.

### FR-021 장애 주입

- 설명: 실습 전용 환경에서 장애를 안전하게 반복 주입한다.
- 입력: 장애 유형(F-1~F-4), 시작·종료 지시
- 기대 동작: 모의 주문 해석 서비스(1차·대체 각각)의 오류·지연 모드를 전환하고, 처리 프로세스를 종료한다. 주입 시각(`injected_at`)을 기록한다.
- 예외 상황: 실습 환경 외 대상 지정
- 인수조건: 장애 주입이 실제 데이터를 바꾸지 않으며, 같은 장애를 반복 주입할 수 있다.

### FR-022 사건 로그와 지표

- 설명: 사건 전 과정을 기록하고 지표를 산출한다.
- 입력: 각 역할의 기록
- 기대 동작: 15장의 필수 항목을 기록하고 MTTD, MTTR, 복구 성공률, 오탐률, 평균 시도, 에스컬레이션율, 회귀 테스트 통과율을 산출한다.
- 예외 상황: 기록 누락
- 인수조건: 모든 사건에 injected_at·detected_at·recovery_started_at·recovered_at(또는 최종 실패 시각)이 존재한다.

### FR-023 운영자 화면

- 설명: 운영자가 사건·복구 상태를 보고 승인한다.
- 입력: 사건 기록, 회로 상태
- 기대 동작: 사건 목록, 단계별 진행, 회로 상태, 승인 요청을 표시한다.
- 예외 상황: 승인 요청 없음
- 인수조건: 승인 요청이 화면에 표시되고, 화면에서 승인·거부가 가능하다.

### FR-024 CI/CD 품질 게이트

- 설명: 변경마다 자동 테스트를 실행하고 실패 시 배포를 차단한다.
- 입력: 코드 변경
- 기대 동작: 단위·통합·주문 정합성·장애 복구 테스트 → 빌드 → 클라우드 배포 → 기본 동작 확인 → 외부 메신저로 결과 알림.
- 예외 상황: 필수 테스트 실패
- 인수조건: 정산 로직에 의도적 오류를 넣은 변경은 배포되지 않고 실패 알림이 전송된다(SC-7). 고정 응답 테스트와 실제 LLM 호출 테스트를 구분한다.

## 14. 비기능 요구사항

### NFR-001 신뢰성

복구 전후로 주문·확인·정산 데이터가 보존되어야 한다. 프로세스가 재시작되어도 시도 횟수·사건 상태·체크포인트가 유지되어야 한다.

### NFR-002 안전성

장애 주입과 자동 복구는 실습 전용 환경 안에서만 동작한다. 12.3의 금지 행동은 어떤 경로로도 자동 실행되지 않는다. 복구 실패 시 잘못된 주문서가 생성되지 않는다.

### NFR-003 보안

- 개인 확인 링크는 추측할 수 없는 무작위 토큰과 24시간 만료를 사용하며, 해당 주문자의 내역만 노출한다. 링크 보유를 접근 기준으로 하며 본인 인증은 하지 않는다.
- 인증정보(API 키 등)는 저장소에 포함하지 않는다.
- 로그에 인증정보와 링크 토큰 원문을 남기지 않는다.

### NFR-004 관측 가능성

모든 사건은 사건 ID와 추적 ID로 탐지부터 종료까지 추적할 수 있어야 한다.

### NFR-005 성능

- 장애 판정: 헬스체크 5초 주기, MTTD 15초 이하
- 정상 응답시간: 기준선을 측정해 기록하고, 복구 후 기준선 2배 이내

### NFR-006 재현성

장애 실험은 모의 의존 서비스로 수행해 같은 조건을 반복할 수 있어야 한다. 정상 흐름은 모의 응답으로 우선 진행하고, 실제 LLM 연결은 후순위로 둔다.

### NFR-007 설명 가능성

진단 결과와 복구 결정에는 판단 근거가 기록되어야 한다. 주문 이벤트에는 원문 메시지 근거가 연결되어야 한다.

### NFR-008 사용성

사용자 화면에는 단계별 진행 상태와 필요한 행동만 표시하고, 기술 오류 메시지는 노출하지 않는다.

### NFR-009 비용

클라우드(AWS EC2 등) 배포는 비용 한도 안에서 운영하고 실습 종료 후 리소스를 정리한다. 한도 금액은 [미결정] (U-02).

### NFR-010 확장성

주문 데이터는 카테고리 → 브랜드 → 상품 → 사양·옵션 → 주문 구조로 설계해 카페 외 카테고리를 추가할 수 있어야 한다. MVP 구현은 카페만 한다.

## 16. 검증 및 완료 기준

### 16.1 검증 지표

| 지표 | 측정 방법 | 목표 |
|---|---|---|
| MTTD | `detected_at - injected_at` | 15초 이하 |
| MTTR | `recovered_at - injected_at` | 5xx·타임아웃 60초 이하, 프로세스 중단 90초 이하 |
| 복구 성공률 | 성공 ÷ 전체 주입 (3종 × 5회) | 80% 이상 |
| 오탐률 | 오탐 ÷ 전체 경보 | 측정·보고 |
| 평균 복구 시도 | 전체 시도 ÷ 성공 건수 | 측정·보고 |
| 에스컬레이션율 | 에스컬레이션 ÷ 전체 장애 | 측정·보고 |
| 회귀 테스트 통과율 | 통과 ÷ 전체 | 100% |
| 데이터 무결성 | 중복·유실·확인 상태 불일치·금액 불일치 | 0건 |
| 배포 차단 | 의도적 실패 변경 중 차단 비율 | 100% |

업무 품질 지표(주문 추출·수정·취소 정확도, 메뉴 매칭 정확도)의 목표 수치는 [미결정] (U-08).

### 16.2 Day 3 데모 계획

Day 1에는 실행하지 않고 방법만 정의한다.

| 순서 | 시나리오 | 주입 방법 | 기대 결과 | 성공 증거 |
|---:|---|---|---|---|
| 0 | 정상 기준선 | 없음 | 주문서·정산 생성 | 정답 데이터 100% 일치, 응답시간 기준선 기록 |
| 1 | HTTP 5xx | 1차 모의 서비스 오류 모드 | 재시도로 정상화 | 사건 로그, MTTD·MTTR, Verification 통과 |
| 2 | 타임아웃 | 1차 모의 서비스 지연 모드 | 재시도 → 대체 서비스 전환 | 사건 로그, 전환·복원 기록 |
| 3 | 프로세스 중단 | 처리 프로세스 종료 | 재시작 + 체크포인트 재개 | 중복·유실 0건, 개인 확인 상태 보존 |
| 4 | 반복 장애·회로 차단 | 1차 오류 모드 유지 | 회로 차단, 자동 복구 중단 | 회로 상태, 자동 시도 0건 |
| 5 | 자동 복구 실패·에스컬레이션 | 1차·대체 모두 오류 모드 | FAILED 보존, 사람 승인 요청 | 화면 승인 요청, 외부 메신저 알림·재알림 기록 |
| 6 | CI 품질 게이트 | 정산 로직에 의도적 오류 | 배포 차단 | CI 실패 기록, 실패 알림 |

### 16.3 PRD 완료 기준

- 시나리오 0~6의 성공 증거를 모두 확보한다.
- 5.2의 성공 기준 SC-1~SC-8을 실험 결과로 보고한다. 미달 항목은 원인과 함께 보고한다.
